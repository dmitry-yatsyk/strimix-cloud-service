# ТЗ: классификация трафика, синтетическая атрибуция и вероятностный матчинг рекламы

> Статус: проект решения, обсуждается. Ветки: `feature/traffic-channel-origin`
> в cloud-management-service и reporting-service.

## 1. Какую проблему решаем

Сейчас Strimix атрибутирует конверсии только через веб-визиты: клик по рекламе
→ сайт с UTM-метками → счётчик записал визит → джоба атрибуции связала визит со
сделкой. Но у многих клиентов конверсии приходят мимо сайта: переписки в
Instagram Direct, лид-формы, CRM, рассылки, звонки. Сделка есть, визита нет —
реклама не получает свою конверсию.

Решение из пяти частей:

1. **Синтетические визиты** — искусственные записи в `visits`, создаваемые из
  событий CRM/мессенджеров, чтобы конверсия без сайта встроилась в обычную
   цепочку атрибуции (first-click, last-click, linear работают без изменений).
2. **Классификация трафика** — колонки `traffic_origin` и `traffic_channel` на
  визитах и расходах, заполняемые по настраиваемым правилам.
3. `attributed_ad` — структура на визите с идентификаторами рекламного
  объекта + новые ярусы матчинга в движке отчётов.
4. **Канонические метки** `source`, `medium`, `campaign`, `content`, `term` —
  общий знаменатель для платного, органического и реферального трафика; для
   рекламы без веб-клика заполняются проекцией из названий рекламных объектов
   (построчно на расходах; на визите — только однозначные значения его
   зарезолвленной группы, неоднозначное поле остаётся null).
5. `landing_page` — нормализованный URL входа, единый параметр для рекламы
  и визитов (поиск лендингов без счётчика).

## 2. Словарь


| Термин                | Значение                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сигнал                | Фрагмент информации об источнике, который клиент передал в параметрах события, заказа или сделки (например `source_id=13`, `ad_name=Промо март`).                                                                                                                                                                                                                                                                                                                   |
| Синтетический визит   | Строка в `visits` с `visit_type='synthetic'`, которую создала джоба из сигналов, а не веб-счётчик.                                                                                                                                                                                                                                                                                                                                                                   |
| Резолюция             | Поиск сигнала (id или названия) в таблице `ad_costs`, чтобы восстановить рекламную иерархию (кампания → группа → объявление) и привязать визит к расходам.                                                                                                                                                                                                                                                                                                           |
| Зарезолвленная группа | Набор строк `ad_costs`, которые резолюция нашла для сигнала этого синтетического визита. Пример: сигнал `ad_name='Промо март'` нашёл три строки расходов с таким названием — эти три строки и есть группа визита. У визита нет колонок `data_source`/`ad_destination` и сетевых названий, поэтому рекламные условия правил и плейсхолдеры проекции на визите берутся из этой группы. Если резолюция ничего не нашла, группы нет и рекламные условия на визите не выполняются. |
| Зерно атрибуции       | Самый глубокий уровень рекламной идентичности, который удалось установить по сигналу: предпочтительно `ad_id`, иначе `ad_name`, иначе adgroup, иначе campaign. Чем глубже зерно, тем точнее разбивка в отчётах.                                                                                                                                                                                                                                                     |
| Канонические метки    | Поля `source`, `medium`, `campaign`, `content`, `term` — общие измерения трафика без привязки к префиксу «utm_». Ими пользуются и платный, и органический, и реферальный трафик.                                                                                                                                                                                                                                                                                     |
| Проекция              | Заполнение канонических меток из названий и идентификаторов рекламных объектов по utm-правилам с плейсхолдерами (`{campaign_name}`, `{ad_name}` и т.д.).                                                                                                                                                                                                                                                                                                            |
| Правило перевода | utm-правило, которое переписывает метку готовым литералом на основе значения из сигнала клиента. Пример: маппинг записал `source='13'` из кастомного параметра заказа, а правило перевода говорит: «если `source` соответствует `^13$`, записать `set_source='instagram'`». Подробно — раздел 3.2. |
| Правило проекции | utm-правило с плейсхолдерами в выходах: метки заполняются данными найденной рекламы — `{campaign_name}`, `{ad_name}`, `{data_source}` и т.д. На строке расходов плейсхолдер разворачивается из её **собственных** сетевых колонок (построчно); на синтетическом визите — из **однозначных** значений его зарезолвленной группы, неоднозначное поле даёт null. Подробно — раздел 3.2. |
| `(combined)`          | **Отображаемое** значение колонки отчёта, когда в бакете строки сидят расходы с разными значениями этого измерения и однозначного показать нельзя. Вычисляется движком отчётов при чтении (раздел 8.1); **в данные не пишется никогда** — ни в метки, ни в `attributed_ad`, ни в сетевые колонки.                                                                                                                                                                                      |


## 3. Таблицы конфигурации (BigQuery-датасет проекта)

Все три создаются при деплое проекта и **один раз** засеиваются системными
правилами (`is_system=true`). Дальше пользователь через CRUD правит и удаляет
любые правила, включая системные — джоба ничего не пересоздаёт и не досеивает.
Новые системные дефолты в уже задеплоенные проекты автоматически не попадают
(отдельная sync-джоба или CRUD-действие «восстановить дефолты»). На этапе MVP
идентификаторы строк прописываются вручную, после появления CRUD он их
перезапишет своими.

### 3.1 `attribution_signal_mappings` — «где лежат сигналы у этого клиента»

> **Пошаговая инструкция для настройщика** (сценарии, сводная схема, типовые
> ошибки): раздел **3.1.1** ниже и отдельный файл
> [`attribution-signal-mappings-instruction.md`](./attribution-signal-mappings-instruction.md).

Каждая строка: `entity` (`order` / `deal` / `event`), `param_source`
(`custom_params` / `event_params`), опциональный `event_name` (триггер по
названию события), `mode`, `priority`, и ключи:

- **Метки:** `source_param_key`, `medium_param_key`, `campaign_param_key`,
`content_param_key`, `term_param_key`, `strimix_refid_param_key`. Все
опциональны, никаких неявных дефолтов: не указал ключ — метка не
заполняется. Максимальный явный контроль.
- **Рекламная идентичность:** `campaign_id_param_key`,
`campaign_name_param_key`, `adgroup_id_param_key`, `adgroup_name_param_key`,
`ad_id_param_key`, `ad_name_param_key`. Названия — это сетевые названия
(колонки `campaign_name`/`adgroup_name`/`ad_name` в `ad_costs`), не
канонические метки.
- `data_source` **клиент не передаёт** — сеть определяется при резолюции из
найденных строк `ad_costs`. Поле нигде на фронте не выводится, оно
техническое.
- **[добавить]** `ad_destination_regex` — граница резолюции: «сигналы этого
маппинга искать только среди объявлений с таким назначением». Для маппинга
инстаграм-лидов — regex на чатовые назначения, чтобы сайтовая тёзка не
попадала в кандидаты. Системные сид-маппинги по умолчанию исключают сайтовые
назначения (синтетический визит по определению рождается мимо сайта); клиент
со сломанным счётчиком сознательно расширяет скоуп.

**Фильтры срабатывания (`match_*_regex`).** Двенадцать опциональных
regex-полей, которые решают, применим ли маппинг к конкретному извлечённому
сигналу:

- по каноническим меткам: `match_source_regex`, `match_medium_regex`,
  `match_campaign_regex`, `match_content_regex`, `match_term_regex`,
  `match_strimix_refid_regex`;
- по рекламной идентичности сигнала: `match_campaign_id_regex`,
  `match_campaign_name_regex`, `match_adgroup_id_regex`,
  `match_adgroup_name_regex`, `match_ad_id_regex`, `match_ad_name_regex`.

Семантика фильтров:

1. Фильтры проверяются **после извлечения** значений этим же маппингом.
   Для заказов и сделок проверка идёт по значениям актуального состояния
   сущности (последнее её событие — см. «состояние, а не история» ниже),
   то есть маппинг решает свою применимость по тем же значениям, которые
   потом попадут в визит.
2. Все непустые фильтры соединяются через **AND**: маппинг срабатывает,
   только когда каждое заданное условие совпало.
3. Строгая семантика пустоты: если фильтр задан, а соответствующее значение
   не извлеклось (ключ не настроен, параметра нет в контейнере или он
   пуст), фильтр считается **непройденным** и маппинг к этому сигналу не
   применяется.
4. Regex оцениваются **с учётом регистра** — ровно как написаны; если нужна
   регистронезависимость, флаг `(?i)` вписывается в сам regex (та же
   конвенция, что и в `traffic_rules`).
5. Null-фильтр означает «условия нет»: маппинг без единого фильтра, как и
   раньше, применяется ко всем своим сигналам.

Зачем это нужно. Фильтры позволяют развести один CRM-поток на несколько
маппингов и дать каждому из них свою границу резолюции
`ad_destination_regex`. Важно понимать механику: фильтр **не переписывает**
колонку `ad_costs.ad_destination` (её источником остаётся коннектор) — он
выбирает, **какой маппинг сработает** на данном сигнале, а у сработавшего
маппинга уже прописан нужный скоуп назначений. «Явно прописать, что это
чат / не сайт» означает: настроить маппинг, который срабатывает по признаку
не-веба (код источника CRM, префикс названия кампании и т.п.) и несёт
`ad_destination_regex` на чатовые/несайтовые назначения.

**Взаимодействие с `priority` — жёсткое требование к реализации.**
Розыгрыш `priority` идёт **только между маппингами, прошедшими свои фильтры
срабатывания** на данном экземпляре `(entity, entity_id)`. Маппинг, не
прошедший фильтр, кандидатом не является и в дедупликации не участвует.
Запрещённая реализация: «взять первый маппинг по `priority`, и если его
фильтр не совпал — не создавать визит и не смотреть остальные». Такой
short-circuit терял бы визиты второго потока. Правильный порядок: сначала
отфильтровать применимые маппинги, затем среди них выбрать один по
`priority`. Следствие: два маппинга со взаимоисключающими фильтрами
(например `^13$` и `^14$`) спокойно живут с одинаковым `priority` — на
каждом экземпляре сущности в кандидатах окажется ровно один из них, и
никто никого не «съест». `priority` реально нужен только когда фильтры
пересекаются или один из маппингов задан вовсе без фильтров.

`mode` — разрешение конфликта с реальной веб-атрибуцией (решение
зафиксировано: нужны оба режима):

- `override` — синтетический визит создаётся всегда; за счёт timestamp
«минус 1 мс» он становится последней маркированной точкой касания перед
конверсией (выигрывает last-click). Для доверенных сигналов — например,
интеграция шлёт атрибуцию лидов Instagram Direct.
- `fallback` — визит создаётся только если у профиля нет ни одного маркированного визита до события; при живом веб-трекинге сигнал молча пропускается. Для сигналов с низким доверием. Кейс, из-за которого режим оставлен: менеджер после входящего звонка спрашивает «откуда вы о нас узнали?» и руками ставит источник сделки в CRM — если у профиля уже есть точный веб-визит с полными UTM, ручной источник не должен красть у него last-click. Direct-заходы без меток веб-атрибуцией не считаются: при них fallback-визит всё равно создаётся.

**Типовые fallback-кейсы (в пользовательскую инструкцию):**

1. **Коллтрекинг.** IP-телефония шлёт вебхук входящего звонка с UTM-метками
  сессии звонящего (динамический коллтрекинг). Маппинг: entity=`event`,
   event_name=`incoming_call`, шесть ключей меток из `event_params`,
   mode=`fallback`. Счётчик записал визит → сигнал молча пропускается
   (синтетический дубль украл бы last-click у настоящего веб-визита); визит
   не зафиксирован (офлайн-носитель, блокировщик, счётчик не успел) →
   создаётся синтетический визит с полными UTM. Рекламной идентичности в
   сигнале нет → резолюция пуста → сид-проекция и рекламные правила визит
   не трогают (раздел 3.2), метки телефонии сохраняются как есть; матчинг с
   расходами — обычным UTM-ярусом, классификация — обычными правилами.
   Нюанс семантики: fallback проверяет «нет ни одного маркированного визита
   до события» — если у профиля был маркированный визит неделю назад, а
   сессия перед звонком не записалась, сигнал пропустится и last-click
   уйдёт старому визиту. Это сознательное поведение режима.
2. **Сквозная аналитика без счётчика (продуктовый кейс).** На сайте нет
  счётчика вообще; UTM доезжают до CRM через скрытые поля форм и приходят
   в `custom_params` заказов/сделок. Маппинг: entity=`order`/`deal`, шесть
   ключей меток, mode=`fallback` — веб-визитов нет, визит создаётся всегда;
   если клиент позже поставит счётчик, сигналы автоматически перестанут
   конкурировать с веб-визитами (бесшовная миграция на полный трекинг без
   смены настроек). Результат: сквозная связка «расходы → лид → сделка →
   ROMI по кампаниям» без Identity Resolution и трекинга посетителей —
   работаем только с готовыми лидами; основа дешёвого/бесплатного тарифа
   «аналитика по лидам» как лид-магнита. Честные ограничения тарифа:
   цепочка касаний профиля состоит из одного синтетического визита —
   first-click/last-click/linear совпадают, мультитач невидим; веб-метрики
   (посетители, сессии, конверсия сайта) пусты.

`priority` **и дедупликация.** Единица извлечения — пара «событие × строка
маппинга» (для любого `entity`): одно событие прогоняется через все
подошедшие строки маппинга, и из каждой такой пары извлекается свой набор
сигналов. Затем каждая пара проверяется фильтрами срабатывания
`match_*_regex` (см. выше): не прошедшие фильтры пары выбывают. Только
после этого выполняется дедупликация **внутри одного типа сущности**.
Группа дедупликации — `(entity, entity_id)`: для order-маппингов
`entity_id` = `order.id`, для deal — `deal.id`, для event — `event_id`
(каждое подходящее событие — отдельный экземпляр). Если на одном
экземпляре сработало (прошло фильтры) несколько маппингов, выигрывает
маппинг с меньшим `priority`. В итоге на каждый экземпляр сущности
создаётся ровно один синтетический визит.

**Семантика заказов и сделок — состояние, а не история (зафиксировано).**
Заказ и сделка обновляются каждым новым событием, которое несёт их данные.
Таблицы `orders`/`deals` строятся по принципу «состояние = последнее
событие» (`last_value` по каждому полю). Извлечение сигналов следует той
же семантике: метки и рекламная идентичность читаются из **актуального
состояния** сущности (параметры её последнего события), а не из первого
попавшегося события. Иными словами, заказ считается на уровне сущности
целиком, а не привязывается к отдельным событиям истории. Якорь же
синтетического визита — **момент создания** сущности (её самое раннее
событие): timestamp визита = создание − 1 мс. Так визит гарантированно
предшествует конверсионному событию, к которому привязана атрибуция
заказа (`attribution_event_id` = первое событие заказа). Следствие: если
CRM дописала или поправила атрибуцию заказа поздним событием, следующий
прогон джобы пересоздаёт синтетику с нуля — визит получает уже актуальные
метки, а якорь по созданию остаётся прежним. Для event-сущностей всё
проще: событие неизменяемо, поэтому и сигнал, и якорь — само это событие.
В джобе это уже реализовано: для order/deal параметры берутся из последнего
события сущности, якорь визита — из самого раннего.

**Кросс-сущностной дедупликации нет — визит на каждый экземпляр сущности
(зафиксировано).** Дедупликация сознательно не пересекает границы типов
сущностей: каждый экземпляр каждой сущности рождает свой синтетический
визит. Несколько событий с разными атрибуциями дают визит на каждое
событие; несколько заказов — визит на каждый заказ; то же со сделками.
Дедупликация схлопывает только повторы **одного и того же** экземпляра:
заказ, который засветился и в `order_created`, и в `order_updated`,
получает один визит — метки берутся из актуального состояния заказа, якорь
ставится по его созданию (см. «Семантика заказов и сделок» выше).
Следствие для настройщика (в пользовательскую инструкцию): событие,
которое одновременно совпало с event-маппингом и с order-маппингом, даст
**два** визита — по одному на каждую сущность. Если это нежелательно,
event-маппинги нужно привязывать через `event_name` к выделенным событиям,
которые не несут заказ или сделку. Это зона настроек: система ведёт себя
детерминированно — если сущность есть, визит будет.

| Интеграция шлёт полноценное «синтетическое page_view»-событие `offline_attribution` со стандартными метками | entity=`event`, event_name=`offline_attribution`, шесть ключей меток = стандартные имена (`source`, `medium`, ...) |
| Instagram Direct: CRM передаёт код сети (`source_id`) и название объявления | entity=`deal`, `source_param_key='source_id'`, `ad_name_param_key='ad_name'`, `match_source_regex='^13$'`, `ad_destination_regex` = non-web; utm-rule `^13$` → `instagram` (§3.1.1) |
| Instagram Direct: только название объявления (без кода сети) | entity=`deal`, `ad_name_param_key='ad_name'`, скоуп назначений — не-web |
| Тёзки web/чат, различимые только кодом источника CRM (`source_id` = 13/14)                                   | два маппинга: `match_source_regex='^13$'` со скоупом не-web и `match_source_regex='^14$'` со скоупом `^web$` (сквозной пример ниже) |
| Признак не-веба зашит в префикс названия кампании (`IG_...` / `WEB_...`)                                      | два маппинга: `match_campaign_name_regex='^IG_'` со скоупом не-web и `match_campaign_name_regex='^WEB_'` со скоупом `^web$`      |


**Сквозной пример фильтров срабатывания: тёзки web/чат, различимые только
кодом источника CRM.** Клиент льёт один и тот же креатив A/B на сайт и в
Instagram Direct; таргетолог завёл в кабинете два объекта с одинаковым
названием `Промо март` — у одного `ad_destination='web'`, у другого
`'chat'` (обе строки лежат в `ad_costs`, значения записал коннектор). CRM
различает потоки полем `source_id`: 13 — Instagram/чат, 14 — сайт.

Исходные данные двух сделок:

```text
Сделка A (Instagram / chat):        Сделка B (web):
  custom_params:                      custom_params:
    source_id = 13                      source_id = 14
    ad_name = Промо март                ad_name = Промо март
    campaign_name = IG_spring_promo     campaign_name = WEB_spring_promo
```

Настройка — два маппинга с одинаковым `priority`:

| Поле | `m_keycrm_non_web` | `m_keycrm_web` |
| --- | --- | --- |
| `entity` / `param_source` | `deal` / `custom_params` | `deal` / `custom_params` |
| `priority` | 100 | 100 |
| `source_param_key` | `source_id` | `source_id` |
| `campaign_name_param_key` | `campaign_name` | `campaign_name` |
| `ad_name_param_key` | `ad_name` | `ad_name` |
| `match_source_regex` | `^13$` | `^14$` |
| `ad_destination_regex` | не-web (например `^(call\|chat\|app\|lead_form\|engagement\|catalog\|multi_destination\|unknown)$`) | `^web$` |
| `mode` | `override` | `override` |

Матчить можно и по префиксу кампании (`match_campaign_name_regex='^IG_'` /
`'^WEB_'`) вместо кода источника, и обоими условиями сразу через AND, если
нужна более жёсткая проверка.

Обработка сделки A (`source_id=13`):

1. Оба маппинга формально подходят по `entity`/`param_source` и извлекают
   `source='13'`, `sig_campaign_name='IG_spring_promo'`,
   `sig_ad_name='Промо март'`.
2. Фильтры: `m_keycrm_non_web` проходит (`13` ~ `^13$`) — кандидат;
   `m_keycrm_web` не проходит (`13` !~ `^14$`) — выбывает.
3. Розыгрыш `priority` идёт среди одного кандидата — побеждает
   `m_keycrm_non_web`.
4. Резолюция ищет `ad_name='Промо март'` в `ad_costs` **только** среди
   несайтовых назначений — находится чатовая строка, сайтовая тёзка
   отсекается границей резолюции.
5. Синтетический визит получает сырую метку `source='13'`; дальше правило
   `traffic_rules` стадии `utm` с **`target='visit'`** (перевод CRM-кода)
   и ad-условиями через `visit_ad_groups` переводит код в `instagram` на
   **визите**. Строки расходов классифицируются **отдельным** конвейером
   (projection + seeds); связка в отчёте — через `attributed_ad`.

Обработка сделки B (`source_id=14`) зеркальна: фильтр проходит только
`m_keycrm_web`, резолюция со скоупом `^web$` находит сайтовую тёзку, а
чатовая строка с тем же названием в кандидаты не попадает. Оба потока
живут параллельно на разных сделках; ни один маппинг не блокирует другой,
потому что приоритет разыгрывается только между сработавшими кандидатами.

### 3.1.1 Связь mapping и `traffic_rules`: пошаговая инструкция

Полная инструкция со **схемой пайплайна** (шаги ①–⑦), разбором каждого блока,
таблицами temp/CTE и сценариями A–D:
[`attribution-signal-mappings-instruction.md`](./attribution-signal-mappings-instruction.md).

Там же — таблица `target`, типовые ошибки. Ниже — только
сводка для навигации по ТЗ.

**Принципы (как читать любой сценарий):**

1. **Две таблицы — два слоя.** Mapping → «откуда прочитать»; `traffic_rules`
   → «что значит».
2. **Два типа сигналов.** Метки → колонки визита; рек. идентичность → поиск
   в `ad_costs` → `attributed_ad` (persist) + `visit_ad_groups` (temp).
3. **Mapping не пишет в `ad_costs`.**
4. **Проекция all-or-nothing** — CRM-код в `source` блокирует автоподстановку
   остальных меток из расходов.
5. **Два независимых конвейера rules** (visits ‖ ad_costs); join в отчёте —
   `attributed_ad` или UTM-ярус 8, не utm rule «визит → cost row».

**Схема и temp-таблицы** — см. instruction: схема ①–⑦ + текстовые таблицы CTE/SQL.

**Сводная таблица сценариев:**

| --- | --- | --- | --- | --- |
| Offline / «откуда узнали» | `source_param_key` only | origin + channel | нет | 8 |

**Сценарий D — `source_id` + название объявления (дополнение к сквозному
примеру выше).** CRM передаёт числовой код сети и сетевое имя объявления,
без `ad_id`:

```text

  ad_name   = Промо март
```

1. Mapping: `source_param_key='source_id'`, `ad_name_param_key='ad_name'`,

4. Проекция UTM **не** стартует (`source` уже заполнен).
5. `traffic_rules` utm: `^13$` → `set_source='instagram'`.
6. `traffic_rules` origin/channel: Meta Ads + Paid Social.
7. Отчёт матчит визит с расходами по **ярусам 2–4** (`attributed_ad` id),

Если параллельно нужен web-поток (`source_id=14`) — второй маппинг с

маппингов в сквозном примере §3.1).

### 3.2 `traffic_rules` — «что значат сигналы»

Все условия nullable; непустые соединяются через AND. Regex-условия
оцениваются **с учётом регистра** — ровно так, как они написаны в правиле.
Если нужна регистронезависимость, флаг `(?i)` нужно явно вписать в сам
regex (например `'(?i)^(facebook|fb)$'`); движок принудительно `(?i)` не
добавляет. Благодаря этому можно точечно переписать только `Facebook` в
`facebook` и не задеть уже каноничный `facebook`. Полный список
колонок-условий:


| Колонка                      | С чем сравнивается                     | Примечание                                                                                                                                                                                                                              |
| ---------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `source_regex`               | каноническая метка `source`            |                                                                                                                                                                                                                                         |
| `medium_regex`               | каноническая метка `medium`            |                                                                                                                                                                                                                                         |
| `campaign_regex`             | каноническая метка `campaign`          |                                                                                                                                                                                                                                         |
| `content_regex`              | каноническая метка `content`           |                                                                                                                                                                                                                                         |
| `term_regex`                 | каноническая метка `term`              |                                                                                                                                                                                                                                         |
| `strimix_refid_regex`        | каноническая метка `strimix_refid`     |                                                                                                                                                                                                                                         |
| `campaign_id_regex`          | сетевой `campaign_id`                  | рекламное условие                                                                                                                                                                                                                       |
| `campaign_name_regex`        | сетевой `campaign_name`                | рекламное условие                                                                                                                                                                                                                       |
| `adgroup_id_regex`           | сетевой `adgroup_id`                   | рекламное условие                                                                                                                                                                                                                       |
| `adgroup_name_regex`         | сетевой `adgroup_name`                 | рекламное условие                                                                                                                                                                                                                       |
| `ad_id_regex`                | сетевой `ad_id`                        | рекламное условие                                                                                                                                                                                                                       |
| `ad_name_regex`              | сетевой `ad_name`                      | рекламное условие                                                                                                                                                                                                                       |
| `ad_destination_regex`       | `ad_destination` строки расходов       | рекламное условие                                                                                                                                                                                                                       |
| `data_source` **[добавить]** | `data_source` строки расходов          | рекламное условие; значения — закрытый набор подключённых коннекторов проекта (`FACEBOOK_ADS`, `GOOGLE_ADS`, `TIKTOK_ADS`, …); в CRUD — выпадающий список источников проекта, не свободный текст; в сид-правилах прописывается системно |
| `url_param_key`              | ключ записи в `url_params` (равенство) | условие, не выход; см. ниже                                                                                                                                                                                                             |
| `url_param_value_regex`      | значение той же записи `url_params`    | опционально к `url_param_key`                                                                                                                                                                                                           |
| `traffic_origin_regex`       | уже вычисленный `traffic_origin`       | только стадия `channel`                                                                                                                                                                                                                 |


`target`: `visit` / `ad_cost` / `both` — к какой сущности применяется правило.
Рекламные условия на синтетических визитах вычисляются через зарезолвленную
группу (блок ниже).

**[добавить] `applies_to_web`** (BOOLEAN, по умолчанию `false`) — расширяет
действие правил стадий `utm`, `origin` и `channel` (target с визитами) на
**веб-визиты**:

- `false` (дефолт) — как всегда: стадия трогает только синтетические
  визиты; метки веб-визитов — факты со страницы, защищены от случайной
  перезаписи (кейс «реальный визит с `utm_source=13`» не пострадает).
- `true` — правило дополнительно применяется к веб-визитам.

Для utm исходное назначение флага — **UTM-алиасы**: осознанная нормализация
веб-меток, когда разные команды таргетологов насорили разными значениями
(`facebook`/`fb`/`Facebook` + `cpc` → единое `facebook_ads` +
`conversions`). Заменяет пилотную мини-джобу `utm_aliases`
(закомментированный блок «PROCESS UTM ALIASES» в
`calculate-events-attribution.sql`) — её функцию полностью поглощают
utm-правила, отдельная таблица не нужна. Кейс настройки и подводный
камень — раздел 6.4. Для origin/channel та же семантика: `true` классифицирует
и веб-визиты, `false`/`null` — только синтетические.

**Рекламные условия на синтетических визитах — через зарезолвленную группу
(зафиксировано).** У визита нет колонок `data_source`/`ad_destination` и
сетевых названий, но к моменту применения правил джоба уже знает, к какой
рекламе визит привязан: резолюция (шаг 1 прогона) нашла конкретные строки
`ad_costs`, и связка «визит ↔ найденная группа строк» живёт во временных
таблицах прогона. Поэтому правило с рекламным условием
(`ad_destination_regex`, `data_source`, `campaign_name_regex` и т.п.),
когда оно проверяется на синтетическом визите, подставляет сравниваемое
значение **из зарезолвленной группы этого визита**. Граничные случаи
разруливаются сами:

- Резолюции не было (чистый CRM-источник вроде «Нетворкінг Василь») —
  привязанной рекламы нет, рекламное условие не выполняется, правило визит
  не трогает. Следствие: сид-проекция не затирает метки синтетических
  визитов интеграций, которые прислали готовые `source`/`medium` без
  рекламной идентичности.
- Значение внутри группы неоднозначно (например, тёзки в разных сетях —
  сеть группы неизвестна) — условие по конкретному значению не
  выполняется. Это честное поведение: правило не угадывает.
- На веб-визитах рекламные условия не выполняются никогда, потому что
  резолюция для них не выполняется; utm-стадия к веб-визитам по умолчанию
  вообще не применяется (кроме правил с `applies_to_web=true`).

Про `url_param_key` + `url_param_value_regex` (решение зафиксировано:
оставляем): это **условия**, а не выходы. Правила ничего не пишут в
`url_params` — переписывание url_params убрано из дизайна. Условие позволяет
классифицировать веб-визит по кастомному query-параметру страницы, которого
нет среди канонических меток (например `placement=instagram_stories`). У
синтетических визитов `url_params` пустые, для них условие не срабатывает
никогда.

Три стадии и полный список выходных колонок (`set_*`):

- `**utm**` — переписывает канонические метки. Выходы: `set_source`,
`set_medium`, `set_campaign`, `set_content`, `set_term`,
`set_strimix_refid` (null = поле не трогать). Здесь живёт трансляция
значений: «source соответствует `^13$` → `set_source='instagram'`»
(замена костыльного `CASE WHEN source_id=13 THEN 'instagram'`).
**[добавить]** плейсхолдеры в значениях `set_`*: `{campaign_name}`,
`{adgroup_name}`, `{ad_name}`, `{campaign_id}`, `{adgroup_id}`,
`{ad_id}`, `{data_source}` — проекция названий/идентификаторов в метки
(раздел 6).
- `**origin**` — вычисляет `traffic_origin` (конкретный источник: «Meta Ads»,
«Google», «Telegram»). Выход: `set_traffic_origin`.
- `**channel**` — вычисляет `traffic_channel` (категория: «Paid Social»,
«Organic Search»), может опираться на уже вычисленный `traffic_origin`.
Выход: `set_traffic_channel`.

**Два типовых вида utm-правил: перевод и проекция.** Для джобы это один и
тот же механизм (условие → выходы `set_*`), никакого технического деления
нет — разница только в содержимом выходов и в источнике данных:

- **Правило перевода (записи значения)** — работает от значения, пришедшего
  **из сигнала клиента**. Полная цепочка: маппинг достал кастомный параметр
  из заказа/сделки/события (`order.custom_params.source_id = 13`) и записал
  его в метку визита (`source='13'`); правило перевода смотрит на эту метку
  и переписывает её литералом: «если `source` соответствует `^13$` →
  `set_source='instagram'`». В `set_*` стоят готовые строки (`instagram`,
  `cpc`), обычно заполняется одно-два поля. Цель — превратить сырое
  CRM-значение (id, внутренний код, «Таргет») в каноническую метку.
- **Правило проекции** — работает от **найденной рекламы**: в `set_*` стоят
  плейсхолдеры (`{campaign_name}`, `{adgroup_name}`, `{ad_name}`,
  `{data_source}`, …). На строке расходов они разворачиваются из её
  собственных сетевых колонок (построчно); на синтетическом визите — из
  однозначных значений зарезолвленной группы (неоднозначное поле → null).
  Обычно заполняет комплект меток сразу. Цель — осмысленные канонические
  метки для не-web рекламы; склейка визита с расходами при этом идёт
  прежде всего через `attributed_ad` (разделы 7–8), метки — последний
  ярус связки.

Оба вида пишут в одни и те же шесть полей и свободно совмещаются на одном
визите: перевод может выиграть `source`, проекция — заполнить остальное
(семантика по полям, следующий блок). Одно правило может даже смешивать
литералы и плейсхолдеры в разных полях.

**Семантика применения правил (зафиксировано).** Стадия `utm` применяется
**по полям**: каждое из шести полей (`set_source`, `set_medium`,
`set_campaign`, `set_content`, `set_term`, `set_strimix_refid`)
разыгрывается независимо от остальных. Джоба берёт все правила, совпавшие
по условиям, сортирует их по `priority` и для каждого поля берёт значение
из первого правила, у которого это поле непустое (null в `set_*` означает
«правило это поле не задаёт»). Деления вроде «правила-переводы могут
писать только source, а правила-проекции — только campaign/content/term»
**нет**: любое правило может задавать любой набор из шести полей, хоть все
сразу. Механизм нужен затем, чтобы несколько правил могли совместно
раскрасить один визит — каждое только в тех полях, которые оно задало и
выиграло по приоритету.
Пример: на одном синтетическом визите совпали правило-перевод (priority
100, задаёт только `set_source='instagram'`) и сид-проекция (priority 1000,
задаёт все поля: `set_source='{data_source}'`, `set_medium='(not set)'`,
а `set_campaign`/`set_content`/`set_term` — из плейсхолдеров). Разыгрывание
по полям: оба правила задали `source` — побеждает перевод (100 < 1000),
поэтому в поле пишется `instagram`; `medium`, `campaign`, `content` и
`term` перевод не задал (null) — они берутся из сид-проекции. Если бы
клиентское правило задало ещё и `set_medium`, оно выиграло бы и `medium`.
При семантике «выигрывает одно правило целиком» сработал бы только
перевод, и визит остался бы без `campaign`/`content`/`term` — матчинг по
названиям был бы мёртв. Стадии `origin` и `channel` применяются как раньше:
побеждает первое совпавшее по `priority` правило целиком (у них один
выход).
**Правила перезаписывают извлечённые маппингом значения** (зафиксировано):
извлечённое значение (например, `source='13'`) остаётся в поле только
тогда, когда ни одно utm-правило это поле не задало. Чтобы сохранить или
облагородить извлечённое значение, нужно завести правило-перевод с
приоритетом выше сида.

**Каскад — межстадийный, внутристадийного нет (зафиксировано).** Стадии
выполняются последовательно, и условия каждой следующей стадии видят
результат предыдущей. Так, `origin`-правила читают **уже переписанные**
utm-стадией метки: правило «`source` соответствует `^instagram$` →
Instagram Direct» видит `instagram`, который записал перевод, а не сырое
`13`. Аналогично `channel`-правила видят уже вычисленный `traffic_origin`.
Внутри же стадии utm все правила видят **исходное** состояние меток —
одно utm-правило не может опереться на результат соседнего utm-правила.
Внутристадийный каскад отклонён сознательно: он превращает один проход по
таблице в отдельный проход на каждое правило и делает результат настроек
труднопредсказуемым. Все нужные кейсы выражаются напрямую через исходные
условия (`^13$`, `data_source`).
Следствие для ситуации «клиентское правило перебило метку только с одной
стороны пары визит/расходы»: после этой модели конфликт полностью уходит
на уровень настроек — модуль детерминирован, сиды согласованы по умолчанию,
а рассинхрон пар — зона ответственности того, кто правит правила.

Примеры сид-правил (реально засеиваются при деплое):


| Стадия  | Условие                    | Результат                        |
| ------- | -------------------------- | -------------------------------- |
| origin  | source `^(fb               | facebook                         |
| channel | traffic_origin `^(meta ads | tiktok ads                       |
| channel | medium `^referral$`        | `set_traffic_channel='Referral'` |

**AI Assistants (ChatGPT, официальный UTM).** OpenAI документирует, что
ChatGPT автоматически добавляет `utm_source=chatgpt.com` к исходящим
referral-ссылкам из поиска/цитирования ([Publishers and Developers

### 3.3 `excluded_url_params` — нормализация `landing_page`

Список regex-ов query-параметров, вырезаемых при нормализации (gclid, fbclid,
utm_*, `srsltid`, `gtm_latency`/`gtm_debug`, `strimix_refid` и др.
трекинговые). `strimix_refid` исключается из
`landing_page` намеренно: это параметр отслеживания для матчинга через
одноимённую колонку, а не параметр выдачи контента. Функциональные
параметры (категория товара) остаются, оставшиеся сортируются.

## 4. Новые колонки данных

В `visits` добавляются: `visit_type` (`web` / `synthetic`),
`traffic_origin`, `traffic_channel`, `landing_page`,
`attributed_ad STRUCT<data_source, campaign_id, campaign_name, adgroup_id,
adgroup_name, ad_id, ad_name, ad_destination>` и `ad_match_type`
(материализованный вердикт матчинга, раздел 8).

**Ключевое решение: в** `attributed_ad` **хранятся только однозначные
значения.** Каждое поле заполняется, только если оно однозначно по всей
зарезолвленной группе визита; неоднозначное поле остаётся null (маркер
`(combined)` в persist не попадает). Детерминированная связка по id идёт
через id-поля (ярусы 2–4); связка по названиям — через `campaign_name` /
`adgroup_name` / `ad_name` с замками `data_source` + `ad_destination`
(имён-ярусы 5–7, раздел 8). Коллизии одинаковых id между сетями отсекаются
полем `data_source` в join, когда оно известно.

`data_source` не передаётся клиентом — значение берётся из найденных строк
`ad_costs`. Если тёзка-объявление найдено сразу в нескольких сетях,
`data_source` неоднозначен и остаётся null — имён-ярусы (строгий замок по
сети) честно промахиваются, связка падает до полной UTM-связки (ярус 8).
Лечится границей `data_source_regex` в маппинге (раздел 3.1): резолюция
ищет только в нужной сети, и `data_source` получается однозначным.

В `ad_costs` добавляются: `traffic_origin`, `traffic_channel`,
`landing_page` (из `landing_page_url`). Поле `ad_destination` — это
константы вида «сайт / чат / лид-форма», а не URL; для заполнения
`landing_page` оно не используется.

## 5. Путь сигнала: от события клиента до визита

> Сводная схема и разбор сценария **`source_id` + `ad_name`** — §3.1.1 и
> [`attribution-signal-mappings-instruction.md`](./attribution-signal-mappings-instruction.md).

Пример: из CRM приходит событие `deal_created`, в `custom_params`:
`source_id=13`, `ad_name=«Промо март»`.

1. **Маппинг.** Строка маппинга: entity=`event`, event_name=`deal_created`,
  `source_param_key='source_id'`, `ad_name_param_key='ad_name'`, скоуп —
   чатовые назначения. Извлечено: source=`13`, сигнал имени «Промо март».
2. **Резолюция** (раздел 7): имя ищется в `ad_costs` внутри скоупа →
  заполняется `attributed_ad` (если однозначно — вплоть до `ad_id`).
3. **Создание визита:** `visit_type='synthetic'`, timestamp = времени события
  **минус 1 мс** (визит гарантированно предшествует конверсии),
   `source='13'`, `url_params` пустые (в них лежат только фактические
   параметры страницы — у синтетики страницы нет). Сигнал, из которого не
   извлеклось ничего, визит не создаёт.
4. **Стадия utm.** Правило перевода `^13$` → `set_source='instagram'`
  переписывает сырой код источника. **Проекция из резолюции здесь не
  срабатывает:** `source='13'` уже заполнен на шаге создания визита, а
  системная проекция требует пустых **всех пяти** меток (§3.1.1, §6).
  Campaign/content/term остаются null, пока их не зададут отдельные utm-правила
  или дополнительные ключи в mapping. Матчинг с расходами идёт по
  `attributed_ad` (ярусы 2–4), а не по полной UTM-связке. Внимание
  настройщика: перевод `^13$` → `instagram` на визите должен иметь парное
  правило с `target`, покрывающим `ad_cost`, если нужна согласованная
  UTM-метка и на стороне расходов.
5. **Стадии origin/channel:** `traffic_origin='Instagram Direct'`,
  `traffic_channel='Paid Social'`.
6. Дальше стандартная атрибуция. Синтетика исключена из веб-метрик фильтром
  `visit_type='web'` в системных метриках.

**Принцип: явный сигнал приоритетнее косвенного.** Если CRM передаёт рекламные
id для сделок, у которых есть полноценные веб-визиты, синтетический визит
«огрубляет» атрибуцию (один `campaign_id` не даёт провалиться до объявления,
как это сделала бы полная UTM-связка веб-визита). Это зона ответственности
настройки маппинга, а не бизнес-логики системы: система ведёт себя
детерминированно и не игнорирует явно переданное. Маппинги следует привязывать
через `event_name` только к событиям не-веб-потоков (лиды из директа, офлайн).
Рекомендации в документацию настроек: не передавать рекламные id для
конверсий, имеющих веб-визиты; при передаче предпочитать наиболее глубокий
идентификатор (`ad_id`/`ad_name`) — он сохраняет полную глубину разбивки.

## 6. Проекция названий — жёсткие требования

Маркер `(combined)` в **данные не пишется никогда**: ни в `attributed_ad`,
ни в сетевые колонки `ad_costs`, ни в канонические метки. Это чисто
**отображаемое** значение, которое движок отчётов вычисляет при чтении,
когда бакет строки покрывает расходы с разными значениями измерения
(раздел 8.1). Проекция названий в канонические метки — косметика для
не-web рекламы, а не несущая конструкция матчинга: склейка визитов с
расходами идёт через `attributed_ad` (id- и имён-ярусы), метки — последний
ярус связки.

Проекция работает двумя симметричными правилами:

- **На строках** `ad_costs` — правила с условием по назначению: метки из
  названий получают все не-web назначения; сайтовые объявления сохраняют
  настоящие UTM из URL (см. скоуп в 6.1).
- **На синтетических визитах** — те же плейсхолдеры, но значения берутся из
  резолюции (зарезолвленной группы визита).

Обязательные требования реализации:

1. **Построчная правда.** Строка расходов сама всё о себе знает: плейсхолдер
   на ней разворачивается из её **собственных** сетевых колонок — каждая
   тёзка получает своё настоящее название кампании/группы. На визите
   плейсхолдер разворачивается из **однозначных** значений его
   зарезолвленной группы; поле, разошедшееся внутри группы, даёт null.
   Метки в persist-таблицах всегда истинны для своей строки: никакой
   строке не дописываются чужие неоднозначности, и визит с явным id
   никогда не увидит «загрязнённые» метки своей рекламы из-за чьей-то
   тёзки.
2. **Одна джоба, один снимок.** Обе проекции (на `ad_costs` и на
  синтетических визитах) считаются в одном прогоне
   `calculate-events-attribution` от одного снимка `ad_costs`. Иначе между
   прогонами возникают окна тихого рассинхрона меток.
3. **Полный комплект меток с обеих сторон.** Сид-правила заполняют комплект
   целиком — включая `source`/`medium`, а не только
   `campaign`/`content`/`term`. У не-web объявлений нет URL, их
   канонические `source`/`medium` пусты и должны задаваться теми же
   парными правилами. Здесь описано содержимое **системного сида по
   умолчанию** — это не ограничение механизма: в `set_source` (как и в
   любое `set_*`-поле) правило может писать что угодно — литерал
   (`facebook`, `instagram`), плейсхолдер или их комбинацию. Дефолтный сид
   выбран так:
   - `set_source='{data_source}'` — плейсхолдер: имя сети (`facebook_ads`);
     на визите с кросс-сетевой группой — null. Выбран потому, что это
     единственное значение `source`, которое джоба может определить сама
     для любой сети без настройки клиента; на него опираются origin-сиды
     по именам сетей.
   - `set_medium='(not set)'` — литерал по веб-конвенции джобы
     (`(not set)` / `(none)` / `(direct)` у веб-визитов).
   Клиент, которому нужен другой `source` (`facebook` вместо
   `facebook_ads`, `instagram` для чатовых объявлений), перекрывает дефолт
   своим правилом с приоритетом < 1000: благодаря пометочной семантике оно
   точечно выигрывает нужное поле и не ломает остальные. Если плейсхолдер
   не нашёл значения, поле остаётся **null**. Если клиент удалил сиды,
   метки остаются null с обеих сторон, и UTM-связка всё равно сходится
   (движок сравнивает через `ifnull(x, '_')`). Пустых строк в метках не
   бывает — только null (нормализация `nullif(trim(...), '')` на
   извлечении); проверка «все пять меток пусты» в правиле «всё или
   ничего» — это проверка на null. Резолюция сама дотягивает предков,
   нужных для разворота плейсхолдеров.
4. **Тёзки склеиваются идентичностью, не метками.** Неоднозначность тёзок
   не «распространяется» по меткам и классификации — она фиксируется в
   `attributed_ad`: неоднозначные id остаются null, а однозначные
   `ad_name` + `data_source` + `ad_destination` включают имён-ярусы отчёта
   (раздел 8). `traffic_origin`/`traffic_channel` каждая строка расходов
   получает свои настоящие (по своим меткам и полям), визит — свои по
   своим правилам.

**Сквозной пример.** Объявление «Промо март» живёт в трёх кампаниях (все —
чатовые):


| Строка ad_costs | ad_name    | campaign_name       |
| --------------- | ---------- | ------------------- |
| 1               | Промо март | Весенняя распродажа |
| 2               | Промо март | Ретаргет тёплые     |
| 3               | Промо март | Лиды директ         |


Проекция на строках расходов — построчно: каждая строка получает
`campaign` = её собственное название кампании, `term='Промо март'` (имя
объявления по шаблону идёт в `term`). Сетевые колонки
`campaign_name`/`adgroup_name`/`ad_name` не меняются вообще; отчёты уровня
рекламного кабинета (по сетевым измерениям, без атрибуции) видят полную
детализацию (раздел 6.2). Синтетический визит с сигналом
`ad_name='Промо март'`: резолюция нашла три строки в трёх кампаниях →
неоднозначные id и `campaign_name` в `attributed_ad` null, но `ad_name`,
`data_source` и `ad_destination` однозначны и записаны; в канонических
метках визита `campaign`/`content` — null (плейсхолдер неоднозначен),
`term='Промо март'`. Склейка в отчёте — имён-ярусом по
`ad_name` + `data_source` + `ad_destination`: все три кост-строки-тёзки
схлопываются в один бакет визита, а колонка «кампания» в этой строке
отчёта показывает `(combined)`, вычисленный при чтении.

Признанные ограничения: переименование объявления в кабинете разносит
историю по разным бакетам (свойственно любому матчингу по названиям);
клиент, переписавший правило проекции с одной стороны, разводит **метки**
сторон (имён-ярусы при этом продолжают работать — они от меток не
зависят).

### 6.1 Где живут правила проекции

Правила проекции — **не хардкод в SQL**, а системные сид-строки таблицы
`traffic_rules` (stage=`utm`). Они поставляются парами: правило с
`target='ad_cost'` для строк расходов и зеркальное правило для
синтетических визитов. Хардкод в SQL сломал бы парадигму редактируемости;
сид-правила клиент может менять так же, как любые другие.

Условием такой пары служит `ad_destination_regex` по нормализованной
таксономии назначений. Эту таксономию пишут коннекторы рекламных сетей, а
кост-джоба прокидывает её в `ad_costs.ad_destination` единообразно для всех
сетей (значение никогда не null):


| Значение            | Смысл                                                                       |
| ------------------- | --------------------------------------------------------------------------- |
| `call`              | звонок (tel:, PHONE_CALL)                                                   |
| `chat`              | переписка (Messenger / WhatsApp / Instagram Direct / TikTok messaging)      |
| `app`               | установка приложения / in-app событие                                       |
| `lead_form`         | нативная лид-форма сети (FB ON_AD, TikTok lead form, Google LOCAL_SERVICES) |
| `engagement`        | вовлечение внутри платформы (страница, пост, видео, профиль)                |
| `catalog`           | каталог / shops / shoppable                                                 |
| `multi_destination` | омниканальные кампании с несколькими назначениями                           |
| `web`               | переход на внешний сайт                                                     |
| `unknown`           | fallback для новых/нераспознанных типов                                     |


**Источник истины для `ad_destination` — коннектор рекламной сети
(зафиксировано).** Окончательное решение «web / chat / lead_form / …»
принимает коннектор по типу/цели кампании в кабинете сети; джоба расходов
прокидывает это значение в `ad_costs` как есть (пустое нормализует в
`unknown`). Переопределять назначение по наличию http(s) в
`landing_page_url` **нельзя**: сети часто кладут в URL адрес платформы
при нативном назначении — кейс «лид-форма Facebook с
`https://facebook.com` в рекламном URL» остаётся `lead_form`, а не `web`.
Примеры маппинга коннектора по типу кампании: store-goals PMax →
`multi_destination`, LOCAL_SERVICES → `lead_form`, MULTI_CHANNEL (App) →
`app`, SEARCH → `web`, ON_AD / lead form → `lead_form`.

Проекцию названий получают все назначения, **кроме** `web`: сайтовые
объявления (как их классифицировал коннектор) сохраняют настоящие UTM из
URL. RE2 в BigQuery не поддерживает lookahead, поэтому в сид-правиле
пишется явный список:
`^(call|chat|app|lead_form|engagement|catalog|multi_destination|unknown)$`.
Новые значения таксономии падают в `unknown` и тем самым покрываются
автоматически.

**Проекция не перезаписывает — «всё или ничего» на строку (зафиксировано).**
Рекламные сети позволяют прописывать UTM в поле трекинга объявления, и
коннектор их выгружает — эти уже заполненные метки трогать нельзя.
Поэтому проекция срабатывает на строку расходов только тогда, когда **все
пять** канонических меток пусты; если заполнена хоть одна — строка не
трогается целиком. Почему нельзя красить по-меточно: объявление с
прописанными только `source`/`medium` получило бы `campaign`/`content`/
`term` из названий, а его реальный веб-визит принёс бы только
`source`/`medium` — полная UTM-связка никогда бы не сошлась.
Две линии защиты работают вместе: от сайтовых объявлений защищает точный
`ad_destination='web'` коннектора (такие строки вне проекционного скоупа),
от частично прописанных UTM — правило «всё или ничего». Следствие: двуликие
назначения (каталог, ведущий на сайт или внутрь соцсети; engagement с UTM
и без) разруливаются построчно сами.

**Соглашение сид-шаблона по меткам (зафиксировано):**
`campaign={campaign_name}`, `content={adgroup_name}`, `term={ad_name}`.
Семантика меток нигде не интерпретируется логикой (проверено): джоба
подставляет плейсхолдеры генерически, а движок использует `content`/`term`
только в equality-join полной UTM-связки. Google-специфика («в term —
ключевое слово») касается web-объявлений, чьи метки приходят из URL и
проекцией не трогаются. Если нужны сетевые различия, сид-правила
разводятся условием по `data_source`. Клиент, настроивший свои правила с
другим порядком меток, отвечает за это сам — на джобу и движок это не
влияет.

### 6.2 Проекция — дописывание меток, а не изменение данных

Проекция дописывает только **канонические метки**. Физически ничего не
агрегируется и не переписывается: строки `ad_costs` остаются построчными,
сетевые поля (`campaign_name`, `adgroup_name`, `ad_name`, все id) не
трогаются вообще. Групповое вычисление существует только на стороне
**визита** (зарезолвленная группа — временная таблица прогона) и даёт
меткам визита однозначные значения либо null.

Следствие: отчёты по сетевым измерениям с метриками из самой таблицы расходов
(расходы, клики, а в перспективе — конверсии и выручка, репортуемые сетью)
сохраняют полную детализацию до объявления и не требуют атрибуции.
`(combined)` в данных не живёт нигде — в отчётах движок отображает его при
чтении в колонках строк визитов (раздел 8.1).

### 6.3 Глубина разбивки в отчётах

Разбивка не может быть глубже зерна атрибуции — глубже информации физически
нет. При разбивке на уровне зерна (например, по `ad_name` для тёзок) строка
визита и его расходы сходятся в одной строке отчёта. При разбивке глубже
зерна (например, по кампании или реальному `ad_id`) расходы честно
раскрываются по своим строкам, а конверсии синтетического визита попадают в
**один** `(combined)`-бакет (групповая семантика ярусов, раздел 8.1):
сигнал «пришло с объявления “Промо март”» не содержит знания, с какого из
трёх ad_id. Это информационный предел, а не баг; поведение описывается в
пользовательской документации.

### 6.4 Сквозной разбор: перевод значений + проекция + матчинг тёзок

Раздел отвечает на три вопроса разом: как совмещаются перевод значений и
проекция, как работает приоритет, и куда девается зерно-имя при тёзках.
Всё происходит **в одной джобе** `calculate-events-attribution`, третьей
джобы и какой-либо спецлогики для тёзок не существует.

**Что такое приоритет и как он разыгрывается.** `priority` — целое число на
каждом правиле, меньше = сильнее (клиентские правила < 1000, сиды ≥ 1000).
Никакой последовательной перезаписи нет: каждое поле вычисляется **один
раз**. Для поля `set_source` джоба берёт все совпавшие по условиям
utm-правила, сортирует по `priority` и берёт значение из первого, у которого
`set_source` непустой. Для `set_medium` — отдельно, и так для каждого поля.
Поэтому на одной сущности «срабатывают» несколько правил одновременно —
каждое в своих полях. На стадиях `origin`/`channel` выход один, там
по-прежнему побеждает одно правило целиком.

**Куда применяется правило.** Поле `target` (`'visit' | 'ad_cost' | 'both'`) уже есть в схеме — оно и определяет, к визитам, к строкам расходов
или к обоим применяется правило. Дополнительных настроек не требуется.

**Исходные данные примера.** CRM-событие `deal_created`:
`source_id=13`, `ad_name='Промо март'`. Реклама — Facebook, чатовые
кампании. Правила в игре:

- **R1** (клиентское, priority 100, `target='both'`): условие —
`data_source` соответствует `^facebook_ads$` и назначение `chat` →
`set_source='instagram'`. (Условие по `data_source` — план работ, п. 4.)
На строках расходов условия проверяются по их колонкам; на синтетическом
визите — по зарезолвленной группе (раздел 3.2): резолюция нашла FB-строки
чатовых кампаний → оба условия выполнены.
- **R2** (сид-пара проекции, priority 1000): назначение не-web →
`set_source='{data_source}'`, `set_medium='(not set)'`,
`set_campaign='{campaign_name}'`, `set_content='{adgroup_name}'`,
`set_term='{ad_name}'`.

**Шаг 1 — извлечение и резолюция** (до всяких правил). Маппинг вытащил
source=`13` и имя «Промо март». Резолюция ищет имя в `ad_costs` внутри
скоупа назначений маппинга:

- Имя нашло **одно** объявление → `attributed_ad` заполнен полностью
(`data_source`, `campaign_id`, `adgroup_id`, `ad_id`).
- Имя нашло **три объявления в трёх кампаниях** (наш случай тёзок) →
неоднозначные id и `campaign_name` не пишутся; однозначное у тёзок —
имя, сеть и назначение → `attributed_ad = {ad_name='Промо март',
data_source='facebook_ads', ad_destination='chat'}`. Зерно-имя **не
теряется**: оно лежит в `attributed_ad.ad_name` и включает имён-ярус
отчёта (шаг 5).

**Шаг 2 — синтетический визит создан.** Пока в нём сырьё: `source='13'`,
остальные метки пустые, `url_params` пустые.

**Шаг 3 — стадия utm, один проход по полям.** Значения плейсхолдеров на
визите вычисляются из его зарезолвленной группы, **только однозначные**
(разделы 6.1–6.2): одна кампания у всех строк группы → её настоящее
название; разные → null. Результат по полям визита:


| Поле     | Кто задал (по приоритету) | Одно объявление       | Три тёзки в трёх кампаниях |
| -------- | ------------------------- | --------------------- | -------------------------- |
| source   | R1 (100 < 1000)           | `instagram`           | `instagram`                |
| medium   | R2 (R1 поле не задал)     | `(not set)`           | `(not set)`                |
| campaign | R2, `{campaign_name}`     | `Весенняя распродажа` | null                       |
| content  | R2, `{adgroup_name}`      | название группы       | null                       |
| term     | R2, `{ad_name}`           | `Промо март`          | `Промо март`               |


Без клиентского R1 поле `source` взял бы сид R2 — плейсхолдер
`{data_source}` дал бы `facebook_ads` (а при тёзках в разных сетях — null).
Извлечённое `13` в любом случае перезаписано правилом (семантика раздела
3.2).

Те же правила применяются к строкам `ad_costs` (R1 — через `target='both'`,
у сид-проекции есть зеркальное правило для расходов), но плейсхолдеры там
разворачиваются **построчно**: каждая строка-тёзка получает своё настоящее
название кампании в метку `campaign`. Метки визита и строк расходов при
тёзках **не совпадают** — и не должны: склейку несут не метки (шаг 5).

**Шаг 4 — стадии origin/channel** (после utm, видят переписанные метки,
побеждает одно правило целиком): например `traffic_origin='Instagram Direct'`, `traffic_channel='Paid Social'`.

**Шаг 5 — матчинг в движке отчётов.** Однозначный случай матчится точно —
ярусом по `attributed_ad.ad_id`. Тёзки матчятся **имён-ярусом**: у визита в
`attributed_ad` лежат `ad_name='Промо март'` + `data_source` +
`ad_destination`, ярус 5 джойнит его к группе кост-строк с тем же именем
внутри той же сети и назначения → расходы трёх кампаний и конверсия падают
в один бакет; колонка «кампания» этой строки отчёта показывает
`(combined)`, вычисленный при чтении (раздел 8.1).

**Рекомендуемый паттерн перевода для рекламных визитов (зафиксировано).**
Односторонний перевод «`source` = `^13$` → `instagram`» с `target='visit'`
не может сработать на строках расходов (там нет «13») и рвёт связку.
Правильный паттерн — как R1: условие по атрибутам рекламы (`data_source`,
назначение), `target='both'`, приоритет выше сид-пары. Обе стороны получают
значение из **одного** правила — рассинхрон парных правок невозможен,
потому что пары нет. Перевод по `source_regex` остаётся для сигналов **без**
рекламной идентичности (чистый CRM-источник): там матчить не с чем, метка
чисто отображательная.

**Кросс-сетевые тёзки — зона настроек (зафиксировано), кейс для
пользовательской инструкции.** Если тёзки раскиданы по разным сетям, у
визита `attributed_ad.data_source` пуст (сеть неоднозначна) — имён-ярусы
промахиваются, правила по атрибутам рекламы на визите не совпадут. Система
эту неоднозначность за клиента не разрешает — рецепт настройки:

1. **Граница резолюции в маппинге** — главный инструмент:
   `data_source_regex` (плюс `ad_destination_regex`) ограничивает поиск
   нужной сетью/назначением, `data_source` и `ad_destination` в
   `attributed_ad` получаются однозначными, имён-ярусы работают.
2. **CRM передаёт явный признак источника** в параметрах события (например,
  `source_id=13` у KeyCRM) — маппинг извлекает его в `source` визита и
   разводит потоки через `match_source_regex`.
3. **Перевод значения** utm-правилом (`^13$` → `set_source='instagram'`,
  `target='visit'`) — косметика меток визита.
4. **Правила origin/channel по меткам** — обе стороны получают одинаковую
   классификацию, если это нужно для разбивок.

Явный сигнал клиента и узкие границы резолюции дают более точную
атрибуцию, чем любой матчинг по совпадению меток.

**Расхождение origin/channel между визитом и расходами — зона настроек
(зафиксировано).** Правила с условиями по сетевым полям (`ad_destination`,
`campaign_name` и т.п., `target='ad_cost'`) не могут сработать на визите —
у визита этих полей нет. Строка расходов получает
`traffic_origin='Instagram Direct'`, её синтетический визит — null. Деньги
при этом матчятся нормально (матчинг идёт по `attributed_ad` и UTM-связке,
origin в нём не участвует) — расходится только **разбивка отчёта** по
`traffic_origin`/`traffic_channel`: расходы и конверсии падают в разные
строки. Правило для настройщика (в пользовательскую инструкцию): **правила
origin/channel для не-web рекламы строить по каноническим меткам с**
`target='both'` — метки после проекции одинаковы у обеих сторон, значит и
классификация будет одинаковой. Условия по сетевым полям использовать
только когда осознанно нужна классификация одних расходов.

Альтернатива — «копирование из группы» (визит наследует метки и
origin/channel готовой копией со строк расходов своей рекламы) —
**отклонена**: требует доработки джобы (отдельный шаг наследования после
полной классификации расходов — на этапе правил копировать нечего, origin/
channel ещё не вычислены) и вводит вторую семантику («правила не действуют
на визиты с рекламой»). Философия зафиксирована другая: система
детерминирована, симметрия — ответственность настройки, сиды дают
корректные пары по умолчанию.

**Кейс «Instagram Direct» (в пользовательскую инструкцию).** Сид
`sys_origin_instagram_direct` **удалён** — он матчил `ad_destination` по
несуществующему в таксономии значению `instagram_direct` (Instagram Direct
входит в `chat`) и никогда не срабатывал. Автоматически отличить Instagram
Direct от Messenger нельзя: у Meta оба — `data_source=facebook_ads` +
`ad_destination=chat`. Различие знает только клиент, например по неймингу
кампаний. Рецепт — правило origin с дополнительным признаком, два варианта:

- **Рекомендуемый:** условие по канонической метке
`campaign_regex='(?i)insta|ig_'` (плюс `source`/`data_source` по вкусу),
`target='both'` → `set_traffic_origin='Instagram Direct'`. После проекции
кост-строки несут свои настоящие названия кампаний в метке `campaign`, и
однозначный визит получает то же значение — классификация совпадёт.
Нюанс: у визита кросс-кампанийных тёзок метка `campaign` = null, условие
по ней не совпадёт — классификация визита честно останется на уровне более
общего правила (Meta Ads).
- **Только расходы:** условие по сетевому полю
`campaign_name_regex` (`target='ad_cost'`) — сработает даже без проекции,
но синтетические визиты этой рекламы останутся без этого origin
(расхождение разбивки, см. выше).

Канальный сид `sys_channel_paid_social` продолжает включать
`instagram direct` в regex по origin — клиентское правило origin
«Instagram Direct» автоматически получит канал «Paid Social».

**Классификация не-web рекламы из коробки.** Дефолтные origin-сиды
платников требуют `source` вида `fb|facebook|...` и `medium` вида
`cpc|ppc|paid...` — у спроецированных не-web строк они не совпадут (`medium`
= `(not set)`). Дефолт закрывается сидами благодаря `{data_source}` в
`source` (требование 3 раздела 6): сеются origin-правила по именам сетей —
«`source` = `^facebook_ads$` → `set_traffic_origin='Meta Ads'`»,
аналогично `google_ads`/`tiktok_ads`/..., `target='both'`, без условия по
`medium`. Обе стороны (строки расходов и синтетические визиты) получают
одинаковый origin, канал подхватывают существующие channel-сиды. Клиент,
которому нужен более красивый `source` (`facebook` вместо `facebook_ads`)
или другой origin, перекрывает это своим правилом с приоритетом < 1000 —
симметрично через `target='both'` (в пользовательскую инструкцию).

**Кейс «коллизия словарей в правилах перевода» (в пользовательскую
инструкцию), зона настроек.** Правило перевода глобально для проекта: оно
не знает, из какого маппинга родился визит, и условие `source=^13$`
совпадёт с **любым** синтетическим визитом, где `source='13'`. Если два
разных источника сигналов используют пересекающиеся коды (KeyCRM:
`source_id=13` = Instagram; другая интеграция: свой код `13` с другим
смыслом), перевод перекрасит оба визита — второй ошибочно. Возраст визита
не защищает: джоба каждый прогон пересоздаёт всю синтетику с нуля и
применяет текущие правила ко всем визитам, старым и новым. Рецепты:

1. **Развести сырые значения** — коллизия существует, только если два
   справочника пересекаются по кодам; следить за уникальностью кодов между
   источниками.
2. **Различающая метка в условии правила** (условия соединяются через AND):
   каждый маппинг дополнительно извлекает свой различающий признак —
   например, маппинг KeyCRM пишет `medium='keycrm'`, второй —
   `medium='other_crm'`; правило перевода сужается до «`source=^13$` **и**
   `medium=^keycrm$` → `instagram`» и чужие визиты не цепляет.

Ограничение (признано): условия «из какого маппинга/события родился визит»
у правил нет — различать синтетику без рекламной идентичности можно только
по содержимому шести меток (`url_params` у синтетики пустые, рекламных
условий без резолюции нет). Если реальный кейс упрётся в нехватку меток
для различения — добавить в правила условие по `event_name`/маппингу
(осознанная будущая доработка, сейчас не делается).

**Кейс «UTM-алиасы: нормализация веб-меток» (в пользовательскую
инструкцию).** Разные команды таргетологов используют разные написания
меток (`facebook`/`fb` + `cpc`), клиент хочет привести их к единому виду
(`facebook_ads` + `conversions`) — и в визитах, и в расходах. Решение —
одно utm-правило: условия `source_regex='(?i)^(facebook|fb)$'` +
`medium_regex='^cpc$'`, выходы `set_source='facebook_ads'`,
`set_medium='conversions'`, `target='both'`, `applies_to_web=true`,
приоритет < 1000. Один проход стадии utm переписывает веб-визиты,
синтетические визиты и строки расходов синхронно.

**Подводный камень для настройщика (обязательно к прочтению).** Правило с
`applies_to_web=true` обязано переписывать **обе стороны симметрично** —
всегда `target='both'`. Если поставить `target='visit'`, метки веб-визитов
перепишутся, а строки расходов останутся со старыми значениями — полная
UTM-связка перестанет сходиться, и весь веб-матчинг этого трафика
развалится (визиты скажут `facebook_ads`, расходы — `facebook`). Это та же
логика парности, что и у правил для синтетики: любая перезапись меток,
участвующих в матчинге, делается одним правилом на обе стороны. Проверка
после настройки: отчёт с разбивкой по `source` — конверсии и расходы
должны лежать в одной строке, а не в двух соседних.

### 6.5 Пошаговый таймлайн одного прогона — с указанием уровня на каждом шаге

Эталонный разбор «для восстановления контекста через месяц». Каждый шаг
явно говорит, **на каком уровне** происходит запись: уровень визита,
уровень расходов или временные таблицы прогона.

**Настройка (одна, заранее).** Правило Р1 в `traffic_rules`: условие
«`data_source=facebook_ads` И назначение=`chat`» → выход
`set_source='instagram'` (литерал), `target='both'` — применяется к двум
уровням: к строкам расходов и к синтетическим визитам.

**Шаг 1. Событие.** Из CRM пришло событие: `source_id=13`,
`ad_name='Промо март'`. Уровень: никакой — сырое событие, ни визита, ни
расходов не касается.

**Шаг 2. Маппинг.** Из события извлечены два фрагмента. Код `13` будет
записан в метку `source` **синтетического визита** на шаге 4 (в расходы
`13` никогда не попадает). Имя «Промо март» используется только для поиска
на шаге 3 и никуда само по себе не записывается.

**Шаг 3. Резолюция.** Джоба ищет «Промо март» **в таблице расходов**
`ad_costs` и находит три строки: Facebook, назначение chat. Эти три строки
становятся зарезолвленной группой будущего визита. Группа сохраняется **во
временную таблицу прогона** (не в `visits` и не в `ad_costs`) как связка
«сигнал ↔ найденные строки расходов» и живёт до конца прогона. Сами строки
расходов при этом не изменились — они только найдены.

**Шаг 4. Создание синтетического визита (уровень визита).** В `visits`
записывается строка: `source='13'` (из шага 2) и `attributed_ad` как
**однозначная выжимка из группы** — пишется только то, что общее у всех
строк группы. Три разных `ad_id`/`campaign_id` поэтому не пишутся; сеть у
всех одна, поэтому `attributed_ad.data_source='facebook_ads'`. Если бы
нашлось одно объявление, записались бы все его id. Полный список строк
группы в визит **не записывается** — он остаётся во временной таблице.

**Шаг 5. Стадия utm, уровень расходов.** У трёх строк группы в их
**собственных колонках** уже стоят `data_source='facebook_ads'` и
`ad_destination='chat'`, поэтому условие Р1 выполнено. Строкам расходов
записывается каноническая метка `source='instagram'` (сетевые поля при
этом не трогаются).

**Шаг 6. Стадия utm, уровень визита.** У визита колонок
`data_source`/`ad_destination` нет, поэтому условие Р1 проверяется по его
зарезолвленной группе **из временной таблицы** (шаг 3). Группа — Facebook +
chat, условие выполнено: визиту записывается `source='instagram'`, а
извлечённый `13` затирается (правила перезаписывают извлечённое, раздел
3.2). Значение `instagram` в обоих шагах 5–6 взято из самого правила
(литерал в `set_source`), а не из группы: группа нужна была только чтобы
ответить на условие «это Facebook chat?». Из группы значения берутся только
через плейсхолдеры (`{data_source}`, `{campaign_name}`, …).

**Шаг 7. Конец прогона.** Временная таблица с группой выброшена. Навсегда
остаётся следующее: на уровне визита — `source='instagram'` и
`attributed_ad.data_source='facebook_ads'`; на уровне расходов —
`source='instagram'` у трёх строк, сетевые поля нетронуты. Метки сторон
совпали, потому что оба уровня покрасило **одно и то же правило** Р1.

Два следа группы, чтобы не путать: `attributed_ad` — **постоянный**, но
хранит только однозначные значения — id, названия, `data_source`,
`ad_destination` (для точных ярусов матчинга в движке
отчётов); временная группа — **полная**, но живёт один прогон (для
рекламных условий правил и плейсхолдеров). На следующем прогоне синтетика
пересоздаётся с нуля, и группа резолвится заново по свежим расходам.

**Группа персональна у каждого визита — правила не «размазывают» чужие
расходы.** Частое ложное прочтение: «раз условие правила — facebook+chat,
то любой чатовый визит получит метки всех не-web расходов проекта». Это не
так, потому что временная таблица из шага 3 — не общий пул «все чатовые
расходы», а **построчная связка** «конкретный сигнал конкретного визита ↔
строки, найденные именно по его имени/id». Группа визита с сигналом
`ad_name='Промо март'` — только строки «Промо март»; строки «Акция апрель»
в неё не входят, хотя они тоже facebook+chat. На стадии utm джоба идёт по
каждому синтетическому визиту отдельно и для каждого использует **его
личную группу** дважды:

1. **Применимо ли правило.** Рекламное условие (`data_source`,
   `ad_destination`, …) проверяется по строкам личной группы. Значение
   внутри группы должно быть однозначным: если две строки chat и одна
   lead_form, назначение группы неоднозначно и условие не выполняется.
2. **Какими значениями красить.** Литералы берутся из самого правила
   (`instagram`), плейсхолдеры — из личной группы, только однозначные:
   `{ad_name}` даёт «Промо март» (не «Акция апрель»), `{campaign_name}` —
   кампанию строк этой группы (если они разные — null).

Следствия: визит с сигналом «Акция апрель» пройдёт то же условие правила,
но получит **свои** метки из **своей** группы. Визит без рекламного сигнала
группы не имеет — рекламные условия на нём не выполняются, поэтому ни
перевод по рекламным условиям, ни проекция его не трогают. Два визита с
одинаковым `ad_name` получат одинаковые группы и одинаковые метки — это
корректно, потому что это одна и та же реклама. Правило одно на всех, но
группа — индивидуальный фильтр: через неё каждый визит видит только свою
рекламу.

## 7. Резолюция рекламной идентичности (в джобе атрибуции)

Резолюция — это поиск в таблице расходов `ad_costs` по сигналам рекламной
идентичности, которые маппинг достал из события/заказа/сделки (id и/или
названия объявления, группы, кампании). Цель: понять, к каким строкам
расходов относится этот синтетический визит.

**Порядок поиска (от точного к грубому).** Сначала ищем на уровне
объявления, если совпадений нет — на уровне группы объявлений, если и там
пусто — на уровне кампании. Более глубокий уровень важнее: как только он
нашёл строки, более грубые для этого сигнала не используются.

**Что сравнивается на каждом уровне.**

1. Если в сигнале есть id этого уровня — сравниваем его с id-колонкой в
   `ad_costs` (`ad_id` / `adgroup_id` / `campaign_id`).
2. Если id в сигнале нет, но есть название — сравниваем название из сигнала
   с колонкой названия в `ad_costs` (`ad_name` / `adgroup_name` /
   `campaign_name`). Это **сетевое название**: имя объекта так, как оно
   лежит в рекламном кабинете и выгружено коннектором, а не каноническая
   UTM-метка (`source` / `campaign` / …).

Сравнение названий **строго с учётом регистра** (зафиксировано): «Промо
Март» и «промо март» — разные объявления и разные расходы;
регистро-независимый матчинг склеивал бы чужие объекты. Это же
гарантирует побайтовое совпадение проекционных меток обеих сторон без
канонизации регистра.

**Ограничения поиска.** До резолюции доходят только сигналы маппингов,
прошедших фильтры срабатывания `match_*_regex` и победивших в дедупликации
(раздел 3.1) — сам поиск фильтры уже не проверяет. Если в маппинге задан
`ad_destination_regex`,
ищем только среди строк `ad_costs` с подходящим назначением (чатовый
сигнал не должен поймать одноимённое сайтовое объявление). По датам
действует логика `click_delay`: при `false` расход и событие должны
попасть в один день; при `true` расход может быть в любой день не позже
дня события.

**Результат поиска.**

- Название/id нашло **одно** объявление → в `attributed_ad` пишутся
  полностью id, названия, `data_source`, `ad_destination`.
- Нашло **несколько** строк (тёзки) → неоднозначные поля в `attributed_ad`
  не пишутся (остаются только значения, общие у всех тёзок — обычно
  `ad_name`, `data_source`, `ad_destination` и общие предки); связка с
  расходами идёт имён-ярусами отчёта, при их промахе — полной UTM-связкой
  (раздел 8).
- Явно переданные клиентом id попадают в `attributed_ad` текущего
  пересчёта даже без совпадений в `ad_costs` — это факт от клиента, и он
  оживёт, когда расходы появятся (API сетей отдают данные с задержкой,
  ручные расходы грузят в конце месяца). В `ad_costs` при этом **не
  записывается ничего**. Самовосстановление обеспечено пересборкой:
  сырые события клиента хранятся постоянно, каждый прогон джоба заново
  извлекает сигналы из них по правилам маппинга, пересоздаёт все
  синтетические визиты с нуля и заново ищет совпадения сигналов в
  актуальной таблице расходов — опоздавшие расходы сматчатся задним
  числом сами.

## 8. Движок отчётов: каскад матчинга

Каждый визит матчится ровно один раз. Ярусы идут по убыванию точности:

1. `strimix_refid` (существующий ярус).
2. `attributed_ad.ad_id` (плюс `data_source`, когда он известен).
3. `attributed_ad.adgroup_id` (плюс `data_source`).
4. `attributed_ad.campaign_id` (плюс `data_source`).
5. `attributed_ad.ad_name` — замки: строгое равенство `data_source` и
   `ad_destination` (null с любой стороны = честный промах).
6. `attributed_ad.adgroup_name` — те же замки.
7. `attributed_ad.campaign_name` — те же замки.
8. Полная UTM-связка (все пять меток + `strimix_refid`, через
   `ifnull(x, '_')`). В новой схеме ярус работает **группами**, как ярусы
   2–7 (см. 8.1), а не построчным join'ом, как в старом движке.

Порядок обоснован так: id — явный, специально переданный сигнал о конкретном
рекламном объекте; сетевое название с замками — точная идентичность более
грубого зерна (случай тёзок); равенство UTM-связки — косвенная улика
(одинаковые метки могут стоять на многих объявлениях). Веб-визиты не имеют
`attributed_ad` и всегда матчатся только на ярусах 1 и 8.

**Принадлежность ярусу материализована джобой.** «Какой ярус съел визит»
вычисляет не отчёт, а джоба атрибуции в конце прогона (после классификации
обеих таблиц): вердикт хранится в колонке `visits.ad_match_type`
(`'strimix_refid'`, `'ad_id'`, `'adgroup_id'`, `'campaign_id'`,
`'ad_name'`, `'adgroup_name'`, `'campaign_name'`, `'utm_labels'`; null =
визит не матчится ни с одной строкой расходов). Ярус отчёта просто
фильтрует `v.ad_match_type = '<свой ярус>'`, uncosted-строки — `is null`.
Раньше эксклюзивность каскада строилась цепочками `not exists` по
предыдущим ярусам, но BigQuery инлайнит CTE в каждом месте ссылки — план
запроса рос экспоненциально от глубины каскада и с восемью ярусами падал с
`resourcesExceeded` ещё на планировании. Свежесть вердикта гарантирована:
`visits` и `ad_costs` меняются только этой же джобой. Потребитель колонки —
только отчёт по рекламе.

Ярусы 2–8 в новом виде включаются только если `data_schema_version` проекта
содержит `attributed_ad` **и** `ad_match_type`. Старые проекты работают на
прежнем SQL байт в байт (ярус 1 + старый построчный UTM-ярус), движок не
падает.

### 8.1 Групповая семантика ярусов 2–8 и честные значения колонок

Все ярусы 2–8 джойнят визит не к отдельным строкам `ad_costs`, а к
**предагрегированной группе** строк: ярусы 2–4 группируют расходы по
`(дата, data_source, id)`, ярусы 5–7 — по
`(дата, data_source, ad_destination, название)`, ярус 8 — по
`(дата, полный комплект меток)`. Визит даёт ровно одну строку выборки
независимо от размера группы.

Это критично для имён-ярусов: кост-строки-тёзки схлопываются в одну
идентичность, и построчный join размножал бы визит по одному разу на
каждую строку группы (при разрезе по сетевым измерениям — кратный счёт
конверсий, расхождение rows с totals).

Значения колонок разбивки для строки визита считаются **честно** по группе:
одно значение у всей группы → значение; значения расходятся → маркер
`(combined)`; значений нет вообще → null. Так конверсии при разрезе глубже
зерна атрибуции попадают в один `(combined)`-бакет (следствие 6.3), а не
размазываются и не теряются. `(combined)` — исключительно отображаемое
значение, вычисляемое движком на лету и только в строках визитов; в данных
он не живёт нигде (раздел 6). Строки расходов всегда показываются с
настоящими сетевыми значениями.

Фильтры отчёта по параметрам применяются к честным (пост-агрегированным)
значениям строки визита.

### 8.2 Кост-строки: расходы без визитов

Строки «расход есть, визитов нет» эмитятся отдельным безусловным блоком:
все комбинации параметров из `ad_costs` периода (без строк яруса 1 — у них
свой путь) с пустым `visit_id`, независимо от того, что случилось с
визитами. Пустой `visit_id` на метрики не влияет (`count(distinct visit_id)`
и join'ы конверсий null игнорируют).

В старом движке такая строка существовала только как побочный эффект
`left join` («визит не нашёлся») и терялась в кейсе «все приджойненные
визиты съедены ранними ярусами»: пара «расход + визит» вычёркивалась из
выборки целиком уже после join, и расход исчезал из rows, оставаясь в
totals. Явные кост-строки закрывают этот баг по построению.

Также в движок добавляется системный параметр `ad_destination` (вывод
колонки в отчёты).

## 9. `landing_page`

На визитах значение берётся из `first_page_url`, на расходах — из
`landing_page_url`. Нормализация общая для обеих сторон: без протокола и
`www.`, минус параметры из `excluded_url_params`, оставшиеся параметры
отсортированы. В отчёте это один параметр: если видны расходы и клики без
визитов, значит на лендинге нет счётчика.

## 10. Декодирование меток (зафиксировано и реализовано)

Трекер парсит query через `URLSearchParams` (form-encoding: `+` → пробел);
рекламные сети отдают метки в том же виде — матчинг держится на совпадении
форматов, отсутствие `+` в метках **корректно**, не чинить. Функция
`decode_uri_component` в джобе приведена к тому же алгоритму (`+` → пробел до
процентного декодирования; литеральный плюс приходит как `%2B`), так что
`url_params` теперь консистентны с метками. Зафиксировано правилом
`utm-label-decoding.mdc` (требует обновления под новое поведение функции).

## 11. Атомарность (в скоупе, больше не отложено)

Единая джоба: расходы считаются первыми, атрибуция второй. Все перезаписи
пользовательских таблиц — через staging-таблицы/`MERGE`, чтобы отчёт,
запущенный во время прогона, не увидел пустые или полупустые
`visits`/`ad_costs`. То же для кост-джоб
(`update-facebook/google/tiktok/manual-costs`), где сейчас DELETE/INSERT.

## 12. Reporting-service (сделано ранее)

Схемы `visits`/`ad_costs` дополнены, параметры
`visit_landing_page`/`ad_landing_page`, скоупы, метрики визитов фильтруют

## 13. Внедрение в существующие проекты

- Джоба атрибуции сама создаёт конфиг-таблицы (`create table if not exists`)
и новые колонки в существующих датасетах — но создаёт их **пустыми**:
системные сид-правила в существующие проекты доставляются отдельно
(одноразовый скрипт миграции на этапе MVP, позже — CRUD-действие
«восстановить дефолты» / sync-джоба).
- После деплоя cloud-части и прогона джобы у проекта поднимается
`data_schema_version` — только после этого движок отчётов включает ярусы
2–8 и новые параметры. Проекты со старой схемой продолжают работать без
изменений.
- Клиентские маппинги (`attribution_signal_mappings`) по определению
индивидуальны — заполняются при подключении клиента.

## 16. Решения, принятые при ревизии ТЗ (для истории)

- Скоуп проекции: **все назначения, кроме** `web` (включая `engagement`,
`app`, `catalog`). Выбор стал безопасным благодаря правилу «всё или ничего»:
перезаписи существующих меток не бывает, проекция лишь заполняет полностью
пустые строки, поэтому расширенный скоуп не несёт риска, а реклама без
меток получает в отчётах названия вместо пустоты (раздел 6.1).
- Проекция «всё или ничего» на строку: срабатывает только когда все пять
канонических меток пусты — защита от частично прописанных UTM в трекинге
объявления (раздел 6.1).
- Условие по `data_source` в `traffic_rules`: предусмотрено дизайном
(раздел 3.2), в коде пока отсутствует — план работ, пункт 4. В UI —
выпадающий список подключённых источников; на MVP используется только
системными сид-правилами.
- `mode`: оставлены оба режима. Кейс, закрепивший `fallback`: ручной источник
сделки от менеджера после входящего звонка не должен красть last-click у
точного веб-визита (раздел 3.1).
- Шаблон проекции: `campaign={campaign_name}`, `content={adgroup_name}`,
`term={ad_name}`; семантика меток логикой не интерпретируется, проверено по
коду движка (раздел 6.1).
- Маркер `(not_provided)` **отменён**. Сид-пара пишет:
`source='{data_source}'` (имя сети), `medium='(not set)'`
(веб-конвенция джобы). Литерал в `source` заменён плейсхолдером, чтобы
не-web реклама классифицировалась origin-сидами по именам сетей.
`campaign`/`content`/`term`/`strimix_refid` при отсутствии значения
остаются null. Если сиды удалены клиентом — метки остаются null с обеих
сторон, UTM-связка не рвётся (`ifnull(x, '_')` в движке). Пустых строк в
метках не бывает — только null (раздел 6, требование 3).
- Пометочная семантика utm-стадии: каждое поле `set_*` независимо берёт
значение из первого по priority правила, задавшего его; стадии
origin/channel — «первое правило целиком». Без этого перевод значений и
проекция были бы взаимоисключающими на одном визите (раздел 3.2).
Следствие: рассинхрон парных правил после клиентских правок — зона
ответственности настройщика, не модуля.
- ~~`(combined)` в `traffic_origin`/`traffic_channel` через сид-правило по
`source = ^\(combined\)$`~~ — **отменено** вместе с материализацией
`(combined)` в данных. Решение ревизии: `(combined)` — исключительно
отображаемое значение при чтении (движок отчётов, раздел 8.1); в метках —
построчная правда на расходах и однозначные-или-null значения на визитах
(раздел 6). Материализация в `ad_costs` загрязняла общие строки расходов
чужой неоднозначностью: визит с явным `ad_id` видел бы `(combined)` в
метках своей рекламы из-за чужого тёзка-сигнала. Соответствующие сид-правила
(`sys_origin_combined`, `sys_channel_combined`) удалены.
- Склейка тёзок перенесена с проекционных меток на **имён-ярусы 5–7**:
`attributed_ad` расширен полями `campaign_name`/`adgroup_name`/`ad_name` и
`ad_destination` (однозначные-или-null); замки имён-ярусов — строгое
равенство `data_source` + `ad_destination`; границы резолюции
`ad_destination_regex`/`data_source_regex` в маппинге делают замки
однозначными (разделы 4, 7, 8).
- Принадлежность визита ярусу каскада **материализуется джобой** в колонку
`visits.ad_match_type` (шаг 10 джобы) — `not exists`-цепочки в отчёте
взрывали план BigQuery экспоненциально от глубины каскада
(`resourcesExceeded` на планировании с восемью ярусами). Вердикт всегда
свежий: обе таблицы меняет только сама джоба (раздел 8).
- Словарь `traffic_label_combinations` (шаг 11 джобы): уникальные комбинации
`date` + канонические метки + `strimix_refid` + `traffic_origin` +
`traffic_channel` из объединения `visits` и `ad_costs` — материализованный
источник для каскадных селекторов фильтров reporting API (включая
кампании без кликов, у которых нет визитов).
- Резолюция и группировка названий — **строго с учётом регистра**: разные
написания = разные объявления и разные расходы (раздел 7).
- Рекомендуемый паттерн перевода значений для рекламных визитов: правило с
условием по атрибутам рекламы (`data_source`, назначение) и
`target='both'` — обе стороны получают значение из одного правила.
Односторонние переводы по `source_regex` — только для сигналов без
рекламной идентичности (раздел 6.4).
- Кросс-сетевые тёзки — **зона настроек клиента**: система неоднозначность
сети не разрешает; рецепт с явным источником из CRM задокументирован как
кейс для пользовательской инструкции (раздел 6.4). Явный `source` от CRM
сужает матчинг до нужной сети — это фича, а не побочный эффект.
- Расхождение origin/channel между синтетическим визитом и его расходами —
**зона настроек**: правила origin/channel для не-web рекламы строятся по
каноническим меткам с `target='both'`. «Копирование из группы»
**отклонено** — лишняя доработка джобы и вторая семантика правил
(раздел 6.4).
- Сид `sys_origin_instagram_direct` **удалён** — матчил несуществующее в
таксономии значение назначения. Кейс «Instagram Direct vs Messenger»
решается клиентским правилом по неймингу кампаний (канонический
`campaign_regex`, `target='both'`); канальный сид Paid Social продолжает
покрывать origin «Instagram Direct» (раздел 6.4).
- Рекламные условия (`ad_destination`, `data_source`, сетевые названия/id)
на синтетических визитах проверяются **по зарезолвленной группе**; без
резолюции рекламное условие не выполняется — сид-проекция не трогает
визиты без рекламной идентичности, метки интеграций не затираются
(раздел 3.2).
- **Правила перезаписывают извлечённые маппингом значения**; извлечённое
остаётся, только если ни одно правило поле не задало. Сохранение/перевод
извлечённого — клиентским правилом с приоритетом выше сида (раздел 3.2).
- Каскад правил — **межстадийный** (utm → origin → channel, каждая стадия
видит результат предыдущей). Внутристадийный каскад отклонён: дорого
(проход на каждое правило) и делает настройки труднопредсказуемыми
(раздел 3.2).
- Классификация не-web рекламы из коробки — origin-сиды по именам сетей
поверх `source='{data_source}'`, `target='both'`, без условия по `medium`
(раздел 6.4).
- Кросс-сущностной дедупликации сигналов **нет** (зафиксировано): каждый
экземпляр каждой сущности (событие, заказ, сделка) рождает свой
синтетический визит; дедупликация схлопывает только повторы одного
экземпляра. Событие, совпавшее с маппингами разных сущностей, даёт визит
на каждую — управляется настройкой `event_name` (раздел 3.1).
- Сигналы заказов/сделок — **«состояние, а не история»**: метки и
идентичность читаются из последнего события сущности (как строятся
таблицы `orders`/`deals`), а якорь визита берётся из момента создания
сущности (− 1 мс). Обновление заказа поздним событием обновляет метки
его визита на следующем прогоне. В джобе это уже реализовано
(раздел 3.1).
- Коллизия словарей в правилах перевода (одинаковые сырые коды из разных
  источников) — **зона настроек**: развести коды либо сузить правило
  различающей меткой из маппинга. Условия «по маппингу» у правил нет —
  осознанная будущая доработка при реальной необходимости (раздел 6.4).
- Источник истины для `ad_destination` — **коннектор рекламной сети**
  (тип/цель кампании в кабинете). Переопределение по http(s) в
  `landing_page_url` **отменено**: URL платформы при нативном назначении
  (лид-форма Facebook с `https://facebook.com`) ошибочно превращал бы
  не-web трафик в `web` и выводил его из скоупа проекции. Джоба расходов
  прокидывает значение коннектора; пустое → `unknown` (раздел 6.1,
  план п. 13).
- Regex-условия `traffic_rules` — **с учётом регистра** по умолчанию;
  регистронезависимость только через `(?i)` в тексте правила. Движок
  больше не добавляет `(?i)` сам: иначе нельзя точечно переписать
  `Facebook` → `facebook`, не задев уже правильный `facebook`. Системные
  сиды, которым нужна широкая нормализация написаний, несут `(?i)` в
  паттерне явно (раздел 3.2).
- UTM-алиасы (нормализация веб-меток из пилотной джобы `utm_aliases`) —
  через флаг `applies_to_web` на utm-правилах вместо отдельной таблицы и
  закомментированного кода. Дефолт `false` сохраняет защиту веб-фактов;
  правила с флагом обязаны быть `target='both'` — симметричная перезапись
  обеих сторон, иначе рвётся веб-матчинг (разделы 3.2, 6.4, план п. 14).
- `url_param_key`/`url_param_value_regex`: остаются как условия (раздел 3.2).
