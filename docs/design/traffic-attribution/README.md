# Strimix: эскизы управления трафиком и атрибуцией

Откройте [галерею семи экранов](gallery.html) или [интерактивный прототип](index.html). Достаточно открыть HTML в браузере: сборка, сервер и доступ к аккаунту не нужны. PNG находятся в [screenshots](screenshots).

Это дизайн-концепция на основе существующего фронтенда и схем, с демонстрационным CRUD в памяти страницы. Подключение к API Plus и BigQuery не реализовано. Изменения сбрасываются после перезагрузки. Фронтенд и рабочий код cloud-management-service не изменялись.

## Предложенная структура

В меню **Проєкт → Трафік та атрибуція** расположен единый раздел с четырьмя вкладками:

| Вкладка | Назначение | Редактирование |
| --- | --- | --- |
| URL-параметри | Очистка нормализованного landing_page | Боковая форма с примером URL |
| Реферали | Исключение доменов из referral-атрибуции | Боковая форма, несколько доменов по строкам |
| Правила трафіку | Перезапись меток, определение источника и канала | Отдельная страница с конструктором |
| Сигнали атрибуції | Извлечение атрибуционных данных из конверсий | Отдельная страница с соответствиями полей |

Раздел помещён в «Проєкт», поскольку настройки действуют на проект и затрагивают как визиты, так и рекламные расходы. Это предложение по навигации, а не существующий маршрут. «Сигнали атрибуції» — пользовательское название `attribution_signal_mappings`.

Простые формы сохраняют контекст списка в боковой панели. Для правил и mappings используется широкая отдельная страница: вложенные поля и разные типы условий плохо помещаются в узкий drawer. Справа показывается живое текстовое описание настроенной логики; это не симуляция расчёта BigQuery.

## Схемы и их влияние на UX

### 1. Исключаемые URL-параметры

Источник: [bigquery.excluded_url_params.schema.ts](../../../src/modules/gcloud/bigquery/schemas/v1/bigquery.excluded_url_params.schema.ts).

Поля формы соответствуют `param_key_regex`, `description`, `is_active`. `param_id` генерируется автоматически; `is_system` показывается как происхождение записи, а не как настройка пользователя.

Шаблон применяется к полному названию ключа без учёта регистра. Очистка касается `landing_page` в визитах и расходах; извлечённые UTM-метки и рекламные идентификаторы не удаляются из полей атрибуции. Поэтому рядом с формой показан пример `utm_source + utm_campaign + category → category`.

Все 15 системных исключений в демоданных взяты из seed-функции. Системные записи доступны для редактирования, отключения и удаления. Их автоматического восстановления нет.

Пример URL использует ограниченный JavaScript regex-предпросмотр. Это не RE2-валидатор и не точная копия BigQuery. В продукте окончательная проверка должна выполняться сервером с семантикой используемого SQL. В частности, текущий SQL собирает общий шаблон и удаляет одинарные кавычки из выражений — это нужно учесть при реализации валидации.

### 2. Исключаемые рефералы

Источник: [bigquery.excluded_referrers.schema.ts](../../../src/modules/gcloud/bigquery/schemas/v1/bigquery.excluded_referrers.schema.ts).

Схема содержит только `hosts: STRING REPEATED`. В ней нет ID домена, описания, происхождения, приоритета и флага активности. Поэтому интерфейс не предлагает эти поля. Строка UI — один элемент массива, а не отдельная BigQuery-строка.

SQL использует точное сравнение с host из списка: `example.com` не означает `www.example.com` или `checkout.example.com`. Ввод URL, путей и wildcard-масок отвергается. Добавление нескольких доменов нормализует регистр и убирает повторы. IDN в этом прототипе вводится в punycode.

Для будущего API предлагается читать все массивы через flatten + deduplicate, а сохранять логический список атомарно в согласованном формате. Версия списка нужна, чтобы два одновременных редактирования не затёрли изменения друг друга. Это предложение API, схема сама его не определяет.

### 3. Правила трафика

Источник: [bigquery.traffic_rules.schema.ts](../../../src/modules/gcloud/bigquery/schemas/v1/bigquery.traffic_rules.schema.ts).

| Блок редактора | Поля и поведение |
| --- | --- |
| Применение | `stage`, `target`, `priority`; `applies_to_web` только для UTM и целей, включающих визиты |
| Условия | Все 6 regex по меткам; data_source; ID/названия кампании, группы и объявления; ad_destination; URL key/value; traffic_origin только на channel-этапе |
| Результат | 6 `set_*` меток на UTM; `set_traffic_origin` на origin; `set_traffic_channel` на channel |
| Дополнительно | `rule_id` только для чтения, `is_active`; `is_system` как badge |

Условия объединяются через **И**, без произвольных OR-групп. Regex чувствителен к регистру; `(?i)` задаётся явно. Синтетический визит не содержит `url_params`, поэтому условие по URL-параметру для него не сработает. Ad-derived условия также не срабатывают для вебвизитов и синтетических визитов без определённой рекламной группы.

Меньшее число `priority` выполняется раньше. UTM выбирает первое подходящее правило **для каждого выходного поля отдельно**. Origin и channel выбирают первое совпавшее правило целиком. Пустое поле результата в форме преобразуется в `null` и не перезаписывает значение.

Дополнительный блок перечисляет семь допустимых placeholders. Правила с placeholders применяются только когда все пять канонических UTM-полей пусты; `strimix_refid` в эту проверку пяти полей не входит. Для расходов используются собственные данные строки, для синтетического визита — однозначные данные рекламной группы.

В таблице нет выдуманного сохраняемого `name`: колонка «Результат правила» вычисляется из stage и outputs. Если нужна отдельная человекочитаемая подпись, следует согласовать новое поле или метаданные API.

В SQL у traffic rules нет явного tie-break по `rule_id` при равном приоритете. Прототип запрещает сохранять два активных правила одного этапа с одинаковым приоритетом. Это предложенная валидация, которой сейчас нет в схеме. Для production нужно определить область уникальности с учётом пересечения `target` и решить, запрещать ли конфликт или показывать предупреждение. Произвольный drag-and-drop пока не предложен: он скрывал бы реальный смысл числового приоритета.

### 4. Mappings сигналов атрибуции

Источник: [bigquery.attribution_signal_mappings.schema.ts](../../../src/modules/gcloud/bigquery/schemas/v1/bigquery.attribution_signal_mappings.schema.ts).

| Блок редактора | Поля и поведение |
| --- | --- |
| Источник | `entity`, зависимый `param_source`, `event_name`, `priority` |
| Соответствия | Все 12 `*_param_key`: 6 меток и 6 рекламных ID/названий |
| Условия применения | Все 12 `match_*_regex`, объединяемые через И |
| Поиск рекламы | `data_source_regex`, `ad_destination_regex` |
| Режим | `fallback` или `override` |
| Дополнительно | `mapping_id` только для чтения и `is_active` |

Для `order` и `deal` разрешён `custom_params`; для `event` — `event_params`. Контейнер выбирается автоматически по сущности: иначе можно создать комбинацию, которую SQL никогда не обработает.

Пустое соответствие означает «не извлекать»: никаких неявных fallback-ключей нет. Должно быть задано хотя бы одно соответствие. Синтетический визит создаётся только если реально извлечено непустое значение.

Условия `match_*` проверяют уже извлечённый сигнал. Если поле отсутствует, заданная для него regex-условие не проходит. Приоритет сравнивается только между прошедшими фильтры mappings для одной сущности. При равном приоритете SQL дополнительно сортирует по `mapping_id`.

`data_source_regex` и `ad_destination_regex` ограничивают набор рекламных расходов для поиска соответствия, а не определяют применимость mapping. Они вынесены в отдельную визуальную группу. В этих двух ограничениях SQL принудительно игнорирует регистр; `match_*` чувствительны к регистру как написаны. Сопоставление рекламных названий точное и чувствительное к регистру.

Для order/deal читается последнее состояние параметров, а визит привязан ко времени создания сущности (в реализации — на 1 мс раньше). Для event источником и временным якорем служит само событие.

- `fallback`: создать синтетический визит, если до события у профиля нет размеченной вебатрибуции.
- `override`: создать визит независимо от вебатрибуции, отдав сигналу приоритет для конверсии.

У mappings нет `is_system` и `description`: такие поля в форме не добавлены. Заголовки в списке вычисляются из конфигурации.

## Границы будущей реализации

Проверен потребляющий [SQL-шаблон](../../../src/modules/gcloud/bigquery/scheduled-queries/templates/update-costs-and-calculate-attribution.sql), а также [deploy-project-resources.ts](../../../src/application/use-cases/project-resources/deploy-project-resources.ts) для контекста создания таблиц. API Plus в этой задаче не исследовался, поэтому распределение обязанностей ниже — предложение:

| Сервис | Предлагаемая ответственность |
| --- | --- |
| Frontend | Списки, формы, локальные черновики, зависимые поля, понятные ошибки, статус операции |
| API Plus | Права проекта, CRUD-контракт, проверка полей и regex, контроль версии, журнал изменений |
| Cloud management | Создание/миграция таблиц; проверить необходимость отдельного внутреннего API записи и интеграции с пересчётом |

Для frontend естественные ресурсы: URL exclusions, traffic rules, attribution mappings — коллекции с ID; referrers — версионируемый список hosts. Новые собственные записи получают `is_system=false` там, где поле существует. Переключение активности — отдельное сохранение одной записи. Удаление требует подтверждения с указанием записи.

Сохранённая конфигурация влияет на последующий расчёт. Нельзя обещать мгновенное изменение отчётов или автоматический пересчёт всей истории: диапазон зависит от запуска attribution job. Кнопка «Пересчитать» не добавлена без согласованного сценария. Аналогично, «Восстановить системные настройки» требует решения, перезаписывать ли пользовательские изменения или добавлять только отсутствующие seed-записи; в этом эскизе такой операции нет.

В deploy-коде отдельно отмечено, что старые проекты могут сохранять legacy view вместо таблицы `excluded_referrers`. Перед включением редактирования для таких проектов понадобится проверить тип ресурса и выполнить отдельную миграцию: текущий deploy автоматически её не делает.

Перед реализацией также нужны состояния загрузки, ошибки запроса/повтор, доступ только для чтения, предупреждение об уходе с изменённой формы и конфликт версии. Прототип демонстрирует заполненные списки, пустой результат поиска, локальную валидацию, подтверждение удаления и сообщения об успешном изменении. Сетевые и ролевые состояния пока описаны, но не имитируются.

## Проверка и файлы

- `index.html`, `styles.css`, `app.js` — автономный интерактивный прототип.
- `data.js` — 15 seed-исключений, 35 seed-правил + 3 демонстрационных собственных правила, 4 демонстрационных домена, 3 mappings.
- `gallery.html`, `screenshots/*.png` — галерея и 7 экспортированных экранов.
- `capture.mjs` — воспроизводимая проверка через локальный Chrome DevTools и экспорт PNG без npm-зависимостей.
- `validation.txt` — результаты 27 проверок: основные CRUD-переходы, зависимые поля, URL-предпросмотр, валидация доменов, отсутствие ошибок JavaScript и переполнения страницы на ширине 1600 и 390 px.

У прототипа нет fetch-запросов и внешних зависимостей. PNG создаются браузером из того же HTML. Пример URL-проверки упрощён; расчёт атрибуции, реальные изменения BigQuery, авторизация и серверная валидация здесь отсутствуют.
