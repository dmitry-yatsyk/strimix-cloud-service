# Traffic & Attribution — runbook релиза

Раздел живёт в трёх репозиториях. Отдельной переменной «включить фичу» нет:
фича существует там, где шлюзу настроен апстрим (`CLOUD_MANAGEMENT_SERVICE_URL`
и `CLOUD_MANAGEMENT_SERVICE_AUTHORIZATION_CODE`), и появляется у того проекта,
который промигрирован. Всё остальное — роль пользователя и, при необходимости,
строка в таблице `featureOverride`.

Путь запроса: `app-frontend` → `app-api-gateway` → `cloud-management-service` → BigQuery.

## Быстрый старт: посмотреть раздел на одном проекте

Ровно то, что нужно сделать, чтобы раздел появился у одного тестового проекта.
Ничего включать вручную не нужно: пункт меню появляется потому, что проект
промигрирован.

**Шаг 0 — узнать id проекта.** Открыть проект в интерфейсе и посмотреть на
адрес: `/organization/3204/projects/7919/...` — первое число организация,
второе проект. Дальше нужен только id проекта.

**Шаг 1 — посмотреть, что миграция сделает (ничего не пишет).** Запускать
из корня `cloud-management-service`; скрипт берёт `.env` этого репозитория —
`MONGO_CREDENTIALS`, чтобы найти датасет проекта, и BigQuery-креды, чтобы
посмотреть таблицы:

```bash
npm run migrate:traffic-settings -- --project=7919
```

В отчёте: строки `[planned]` — что будет сделано, `[already_current]` — что
уже на месте, `[skipped]` — что трогать нельзя без разбора руками (см. 1a).
В конце блок `readiness`: у непромигрированного проекта там `migration_required`
или `not_provisioned` — это и есть причина, по которой пункта меню пока нет.
Если вместо отчёта проект `FAILED` с сообщением про отсутствующий датасет —
у него в BigQuery ничего не развёрнуто, берите другой.

**Шаг 2 — применить.** Тот же запуск с `--apply`:

```bash
npm run migrate:traffic-settings -- --project=7919 --apply
```

Ждём, пока все четыре ресурса покажут `ready`:

    readiness after:
      excluded-url-params: ready read=true write=true
      excluded-referrers: ready read=true write=true
      traffic-rules: ready read=true write=true
      attribution-signal-mappings: ready read=true write=true

Прогон идемпотентен: повторный `--apply` на готовом проекте сообщит
`already_current` и ничего не тронет.

**Шаг 3 — посмотреть в интерфейсе.** Перезагрузить страницу. Пункт «Трафик
и атрибуция» появится в сайдбаре и в карточке проекта на домашней странице
в течение 30 секунд — столько шлюз держит в кэше ответ readiness. Ни рестарт
шлюза, ни пересборка фронтенда не нужны.

Если пункта нет, спросить шлюз напрямую — он сам скажет, какой гейт закрыл:

```bash
curl -s -b cookies.txt \
  "http://localhost:5001/api/v1/organization/3204/projects/7919/features" | jq
```

| Ответ | Что делать |
| --- | --- |
| `state: "available"` | Пункт рисуется; если его не видно — чистить кэш браузера |
| `reason: "NOT_PROVISIONED"` | Миграция не доехала: вернуться к шагу 2 и смотреть `readiness after` |
| `reason: "DISABLED"` | В `.env` шлюза нет `CLOUD_MANAGEMENT_SERVICE_URL` и `..._AUTHORIZATION_CODE` (нужен рестарт шлюза), либо у этого тенанта стоит отключающая строка `featureOverride` (раздел 3a) |
| `reason: "NOT_PERMITTED"` | У пользователя роль без права `trafficSettings.read` |

Все проекты сразу — раздел 1a. Как это устроено — ниже.

## Где какой переключатель

Смотрите таблицу, а не ищите по репозиториям:

| Что нужно изменить | Где | Эффект |
| --- | --- | --- |
| Показать раздел на одном проекте | запустить миграцию этого проекта (раздел 1a) | Только этот проект. Рестарт не нужен, пункт появляется в течение 30 секунд |
| Включить фичу в окружении | настроить `CLOUD_MANAGEMENT_SERVICE_URL` и `..._AUTHORIZATION_CODE` в `.env` шлюза | Без них апстрима нет: маршруты отвечают 404, пункт скрыт. Нужен рестарт шлюза |
| Открыть или закрыть фичу одному тенанту | строка в таблице `featureOverride` (раздел 3a) | Только эта организация или проект, без рестарта |
| Гейты фичи: план, роли, стадия, readiness-проверка | `app-api-gateway/src/config/features.js` | Единственное объявление гейтов; и `GET .../features`, и маршруты читают его |

Почему нет булевой переменной «фича включена». Гейты в реестре отвечают на
вопросы про пользователя и проект — роль, план, готовность. Оставался вопрос
«а держит ли это окружение фичу вообще», и на него уже отвечает конфигурация:
маршруты `/traffic-settings` — это прокси, и без адреса и секрета CMS за ними
нет никого. Поэтому гейт выводится из самой конфигурации
(`app-api-gateway/src/services/features/deployment.js`), а не из отдельного
флага, который можно было бы выставить в противоречии с ней. Настроено —
фича есть; не настроено — нет, и маршруты, и меню отвечают одинаково.

Половинчатая настройка — это ошибка, а не выбор: если задать адрес без секрета
(или наоборот), шлюз не стартует и скажет, чего не хватает. Так фича не может
тихо исчезнуть из-за забытой переменной.

На фронтенде переключателя нет: он рисует то, что сказал `GET .../features`.

## 0. До любой выкатки

CMS пускает на все маршруты traffic-settings только одного именованного
вызывающего — шлюз (`requireTrustedApp('APP_API_GATEWAY')`,
`src/presentation/middleware/trusted-app.middleware.ts`). Это строже, чем
`authMiddleware`, который принимает любой внутренний сервис: эти маршруты
действуют от имени конечного пользователя, чьи права проверил только шлюз.

Поэтому в `APP_AUTHORIZATION_CODES` окружения CMS нужна ещё одна запись:

```json
{ "appName": "APP_API_GATEWAY", "authCode": "<new secret>" }
```

Тот же секрет кладётся в шлюз как `CLOUD_MANAGEMENT_SERVICE_AUTHORIZATION_CODE`.
Без этой записи каждый маршрут отвечает 401, и UI показывает раздел как
недоступный, а не «ломается».

## 1. Cloud Management Service

Выкатывать первым — без него шлюзу некого звать, а пока шлюз сам не зовёт,
это no-op.

Окружение:

| Переменная | Назначение |
| --- | --- |
| `APP_AUTHORIZATION_CODES` | Должна содержать запись `APP_API_GATEWAY` из шага 0 |

Затем мигрировать существующие проекты. По умолчанию — dry run; `--apply`
включается явно:

```bash
npm run migrate:traffic-settings -- --project=7914          # только отчёт
npm run migrate:traffic-settings -- --project=7914 --apply
npm run migrate:traffic-settings -- --all                    # отчёт по всем тенантам
npm run migrate:traffic-settings -- --all --apply
```

Проекты обрабатываются по одному специально: каждый запускает BigQuery-джобы
против своего датасета, и параллельный проход превратил бы обслуживание
в пик нагрузки.

Отчёт называет семь шагов на проект:

1. `verify stored table references` — ссылка, указывающая за пределы датасета
   проекта, только сообщается, никогда не чинится: это может значить, что
   записи двух тенантов перепутаны, и угадать починку хуже, чем остановиться.
2. `create revisions table` — `traffic_settings_revisions`, токен
   optimistic-locking на каждый ресурс.
3. `initialise revision rows` — вставляет только те ресурсы, у которых строки
   ещё нет.
4. `convert excluded_referrers to one row per host` — старое представление
   или таблица с одной строкой и массивом `hosts` становится одной строкой
   на хост с id и флагом `is_active`. Новая таблица собирается под временным
   именем и подменяется, так что `excluded_referrers` отсутствует на два
   metadata-операции, а не на всю загрузку. Если нормализация изменила бы
   набор исключений, шаг сообщает, что изменилось бы, и ничего не пишет.
   Он идёт до проверок колонок, потому что именно ту таблицу, которую он
   оставляет, эти проверки затем смотрят.
5. `add missing columns to <table>` — четыре таблицы настроек старше этой
   работы, поэтому колонки только добавляются, никогда не удаляются и не
   меняют тип.
6. `check stored exclusion patterns against the new logic` — см. шаг 4 ниже.
7. `refresh attribution scheduled query` — в dry run печатает краткий diff
   развёрнутого запроса и ожидаемого. Attribution-джоб читает активные строки
   referrer, поэтому его нужно обновить вместе с шагом 4. Если шаг 4
   `skipped`, этот шаг тоже `skipped`: новый текст запроса читает `is_active`,
   а старая таблица его ещё не имеет. Оба шага двигаются только вместе.

Проект готов, когда блок readiness сообщает `ready` по всем четырём ресурсам.

Необязательная smoke-проверка против реального датасета: все statements
в режиме dry-run BigQuery, ничего не пишется:

```bash
npm run dryrun:traffic-settings -- --project=7914
npm run dryrun:traffic-settings -- --all --limit=1
```

Новым проектам ничего из этого не нужно: `deploy-project-resources` создаёт
таблицу ревизий и засевает её строки.

## 1a. Миграция всех существующих проектов, чтобы раздел появился

У существующего проекта пункта «Traffic & Attribution» нет, пока его не
мигрировали: readiness-проверка отвечает `migration_required` или
`not_provisioned`, и шлюз прячет фичу, которая не развёрнута. Миграция
проекта и есть то, что показывает пункт — отдельно на проект ничего
включать не нужно.

**Шаг 1 — dry run по всем тенантам и сохранить лог.** Ничего не пишется,
поэтому это безопасно в любой момент и можно повторять.

```bash
npm run migrate:traffic-settings -- --all 2>&1 | tee /tmp/traffic-settings-dry-run.log
```

Последняя строка считает, чему нужно внимание:

    Done. 84 project(s), 0 failed, 3 with skipped steps.

**Шаг 2 — посмотреть проекты, которые не чистые.** Машиночитаемый список,
с `--json` в stdout только отчёт:

```bash
npm run migrate:traffic-settings -- --all --json > /tmp/traffic-settings.json
jq -r '.[] | select(.failed or ([.steps[].status] | index("skipped"))) | .projectId' \
  /tmp/traffic-settings.json
```

Три вещи останавливают проект, и ни одну из них не стоит форсировать:

- `FAILED` — обычно у проекта нет зарегистрированного датасета. У такого
  проекта таблиц настроек никогда не было, мигрировать нечего.
- пропущен `verify stored table references` — сохранённая ссылка указывает
  за пределы датасета проекта. Это может значить, что записи двух тенантов
  перепутаны, поэтому сообщается и никогда не чинится автоматически.
- пропущен `convert excluded_referrers to one row per host` — нормализация
  изменила бы набор исключений. В деталях назван каждый хост, который
  изменился бы. Сначала поправить эти значения в старой таблице и прогнать
  проект снова.

**Шаг 3 — apply.** Начать с нескольких проектов, которые можно проверить
глазами, затем остальные:

```bash
npm run migrate:traffic-settings -- --project=7914,7919 --apply
npm run migrate:traffic-settings -- --all --apply 2>&1 | tee /tmp/traffic-settings-apply.log
```

Проекты обрабатываются по одному — каждый запускает BigQuery-джобы против
своего датасета, и параллельный проход превратил бы обслуживание в пик
нагрузки. Прогон идемпотентен: уже мигрированный проект сообщает
`already_current` и его не трогают, поэтому повторный `--all --apply` после
починки нескольких проектов — обычный способ довести работу до конца.

**Шаг 4 — проверить, что раздел появился.** Отчёт каждого проекта заканчивается
блоком readiness, и все четыре ресурса должны читать `ready`:

    readiness after:
      excluded-url-params: ready read=true write=true
      excluded-referrers: ready read=true write=true
      traffic-rules: ready read=true write=true
      attribution-signal-mappings: ready read=true write=true

Снаружи тот же ответ без открытия браузера:

```bash
curl -s -b cookies.txt \
  "$GATEWAY/api/v1/organization/3129/projects/7755/features" | jq
```

`state: "available"` значит, что пункт нарисован. Рестарт и сброс кэша
не нужны: шлюз кэширует readiness на 30 секунд, поэтому пункт появляется
в течение полминуты после миграции, по проекту, сам.

Если всё ещё не появляется, порядок проверки — порядок гейтов: настроен ли
апстрим CMS в шлюзе (`reason: "DISABLED"`), нет ли отключающей строки
`featureOverride` (тоже `DISABLED`), даёт ли роль `trafficSettings.read`
(`NOT_PERMITTED`), мигрирован ли проект (`NOT_PROVISIONED`). Поле `reason`
в ответе называет, какой гейт закрыл, угадывать не нужно.

## 2. API Gateway

Окружение:

| Переменная | Назначение |
| --- | --- |
| `CLOUD_MANAGEMENT_SERVICE_URL` | Базовый origin, без суффикса `/api/v1`. Вместе со секретом включает фичу в этом окружении |
| `CLOUD_MANAGEMENT_SERVICE_AUTHORIZATION_CODE` | Секрет из шага 0 |
| `CLOUD_MANAGEMENT_SERVICE_TIMEOUT_MS` | Необязательно, положительное целое |

Обе первые проверяются на старте: если задана одна из них — вторая обязательна,
и процесс сообщает все проблемы сразу, а не падает при первом использовании.
Если не задана ни одна, шлюз стартует как раньше и фичу не предлагает.

Выкатывать можно сразу с настроенным апстримом: пункт меню всё равно появится
только у промигрированных проектов, а smoke-тест против маршрутов уже возможен.

## 3. Frontend

Конфигурировать нечего: сборка не принимает новых аргументов, а `Dockerfile`,
`cloudbuild.yaml` и workflow деплоя эта фича не трогает.

Видимость — это ответ сервера. Клиент спрашивает
`GET /organization/{id}/projects/{id}/features` и рисует пункт только когда
этот ответ разрешает, поэтому пока шлюзу не настроен апстрим CMS, пункт скрыт
даже в уже выкаченном бандле. Порядок здесь не важен: фронтенд можно выкатить
раньше всего, и пункт появится сам, как только шлюз начнёт отвечать.

Маршруты регистрируются всегда. Прямой URL рисует объясняющее состояние —
«нет доступа», «раздел выключен» или диагноз readiness — а не 404.

## 3a. Реестр фич на шлюзе

`GET .../features` не специфичен для этого раздела: он отвечает по каждой
фиче из `app-api-gateway/src/config/features.js`, и у клиента нет другого
способа решить, что рисовать. Каждая запись объявляет свои гейты, резолвер
применяет их в фиксированном порядке и сообщает первый, который закрыл:

| Reason | Смысл |
| --- | --- |
| `DISABLED` | В окружении не настроен апстрим фичи, или строка `featureOverride` отключает её для этого тенанта |
| `EXPERIMENT_OFF` | Ещё экспериментальная и не открыта для этой организации или проекта |
| `PLAN_REQUIRED` | Тарифный план её не включает |
| `SUBSCRIPTION_INACTIVE` | Подписка истекла или приостановлена |
| `NOT_PERMITTED` | Роль пользователя не даёт права на чтение |
| `NOT_PROVISIONED` | Для этого проекта ещё не развёрнута |

Закрытая фича сообщается как `hidden` или `locked`. Блоки по плану по умолчанию
`locked`, чтобы можно было показать апгрейд; всё остальное прячет фичу.
Пользователю без права никогда не отказывают во всей карте — одна недоступная
фича не должна опустошать навигацию.

Два гейта ничем не открываются: проверка роли и, для проектной фичи, факт
развёртывания. Override — это пилот, а не способ раздать права.

Пилоты и переключатели на тенанта живут в таблице `featureOverride` базы
шлюза, создаваемой голым `sync()` на старте, как `sharedReportGrant`. Строка
с `projectId` целится в этот проект, строка только с `organizationId` —
в всю организацию, и проектная строка побеждает. `isEnabled = 1` открывает
экспериментальную или закрытую планом фичу, `isEnabled = 0` забирает
выпущенную фичу у одного тенанта, не трогая остальных:

Таблица `featureOverride` в core-базе шлюза (та же, где `sharedReportGrant`).
Колонки, ровно как их создаёт модель:

| Колонка | Что писать |
| --- | --- |
| `featureKey` | Ключ из реестра, для этого раздела — `traffic_attribution` |
| `organizationId` | id организации, либо `null` |
| `projectId` | id проекта, либо `null` |
| `isEnabled` | `1` открыть, `0` закрыть |
| `note` | Зачем строка существует, свободный текст; по нему потом видно забытый пилот |
| `createdBy` | id пользователя, кто вставил, либо `null` |
| `createdAt`, `updatedAt` | `now()` — обязательны, у модели включены timestamps |

Заполнено ровно одно из двух: `projectId` — строка про этот проект,
`organizationId` без `projectId` — про все проекты организации. Пара
`featureKey + organizationId + projectId` уникальна.

```sql
-- открыть фичу для одного проекта
insert into featureOverride
    (featureKey, organizationId, projectId, isEnabled, note, createdBy, createdAt, updatedAt)
values ('traffic_attribution', null, 7919, 1, 'пилот', null, now(), now());

-- закрыть фичу всей организации, не трогая остальных
insert into featureOverride
    (featureKey, organizationId, projectId, isEnabled, note, createdBy, createdAt, updatedAt)
values ('traffic_attribution', 3204, null, 0, 'жалоба, разбираемся', null, now(), now());

-- посмотреть, что вообще настроено руками
select id, featureKey, organizationId, projectId, isEnabled, note, updatedAt
from featureOverride
order by updatedAt desc;

-- вернуть тенанта к общему правилу
delete from featureOverride
where featureKey = 'traffic_attribution' and projectId = 7919;
```

Изменения подхватываются в течение 30 секунд (столько шлюз кэширует
overrides), рестарт не нужен. Строку с `isEnabled = 1` не нужно вставлять,
чтобы показать раздел промигрированному проекту — он покажется сам; она нужна
только чтобы открыть фичу, закрытую стадией или тарифом.

Ответы кэшируются в памяти сильно меньше минуты — план на 60 секунд,
overrides и readiness на 30 — поэтому одна загрузка страницы стоит максимум
одного вызова к каждому upstream. Недоступный upstream оставляет свой гейт
открытым и держит последний известный ответ, а не опустошает навигацию;
собственные маршруты фичи по-прежнему применяют свои правила. Traffic &
attribution сегодня не объявляет требования к плану, поэтому к tenant-сервису
за неё не ходят вообще.

## 4. Что делает пересчёт атрибуции

Шаг 7 миграции заменяет текст scheduled query, в том числе чинит логику
URL-исключений, которая старше этой работы. Исправлены три дефекта:

- сохранённый паттерн матчился с целой парой `key=value`, а не с ключом,
  поэтому `^gclid$` никогда ни с чем не совпадал;
- паттерны склеивались в одну альтернацию, и один сломанный паттерн
  отключал все остальные;
- ветки `ad_costs` и `visits` расходились, поэтому один и тот же адрес
  нормализовался по-разному в зависимости от того, какая ветка до него
  дошла.

Для каждого provisioned-проекта сохранённые паттерны проверены, и ни один
из них поведение не меняет — это и есть отчёт шага 6. Остаётся одно
различие, зависящее от данных: query-параметр без значения (`?utm_source&x=1`)
теперь исключается паттерном по своему ключу, а раньше — нет. Если такое
есть в истории проекта, пересчитанный `landing_page` этих визитов изменится.

Пересчёт покрывает всю историю и идемпотентен, поэтому повторный прогон
на проекте, чьи паттерны поведение не меняют, даёт тот же результат.

## 5. Откат

Забрать фичу у одного тенанта — вставить отключающую строку `featureOverride`
(см. 3a): без рестарта и без выкатки. Убрать раздел целиком — убрать
`CLOUD_MANAGEMENT_SERVICE_URL` и `..._AUTHORIZATION_CODE` из окружения шлюза
и перезапустить его; раздел исчезает у всех клиентов сразу, пункт сайдбара
тоже, потому что он следует карте фич. Пересборка фронтенда не нужна.

Большинство изменений BigQuery аддитивны (новая таблица, новые колонки)
и могут остаться на месте. Исключение — конвертация referrer: она заменяет
старое представление или массив `hosts` одной строкой на хост, и attribution
query переписан читать эти строки. Два изменения связаны — откатить только
текст запроса значило бы оставить его читать форму, которой уже нет. Сам
набор исключений переносится без изменений, поэтому шаг отказывается
работать, когда нормализация его изменила бы; откат значит восстановить
и предыдущий текст запроса, и предыдущую форму таблицы из снимка,
сделанного до прогона.
